# P2P Compatibility Policy

This document declares bitcoin-rs's peer-wire compatibility contract with Bitcoin Core and the rules for keeping it pinned.

## 1. Scope and Authority

This policy applies to the P2P transport and peer-protocol surface of `bitcoin-rs-p2p` (`crates/p2p`), including `ActiveChainQuery` (`crates/p2p/src/chain_query.rs`), and the network flags of the node binary. It is the peer-visible counterpart to `docs/policies/source-compatibility.md` (toolchain) and the RPC compatibility manifest (`crates/rpc/src/manifest.rs`, rendered as `docs/rpc-reference.md`).
The decoded command inventory is owned by `crates/p2p/src/compat.rs` (`COMMANDS`, `PINNED_CORE_VERSION`). This document owns the handshake fields, the reject-or-ignore matrix, the deviation ledger, and the verification process. Where this document and prose comments disagree, this document wins; where it and the code disagree, the code is the defect. The §5 table is a hand-maintained projection of `COMMANDS`, updated in the same change-set as the table it projects.

| Setting | Value |

### 2.1 Version-Bump Rules

Re-pinning to a newer Core version requires all of: (1) a passing run of `scripts/run-p2p-core-interop.sh` against the new version with evidence stored under `docs/benchmarks/`; (2) a diff of the message set below against the new version's `net_processing`, with every delta implemented or added to the deviation ledger (§7); (3) updating this document's pin, `crates/p2p/src/compat.rs::COMMANDS`, and the deterministic fixtures in the same change-set: no intermediate states where the table and the code disagree (anti-shim rule, `docs/policies/source-compatibility.md` §5). The fuzz target `p2p_message` consumes `COMMANDS` directly.

## 3. Transport and Envelope

- Bitcoin P2P **v1 envelope** (`crates/p2p/src/wire.rs`): 4-byte network magic, 12-byte NUL-padded command, `u32` little-endian payload length, 4-byte checksum (first 4 bytes of double-SHA256 of the payload), then the payload.
- BIP324 v2 is on by default (`--v2transport`, as Core's `-v2transport`), with v1 detection and fallback (`crates/p2p/src/transport.rs`, `bip324.rs`); message payloads capped at `MAX_MESSAGE_PAYLOAD` (`crates/p2p/src/bip324/reader.rs`). Live interop with Core 31.1 in both directions is recorded (https://github.com/gosuda/bitcoin-rs/pull/1612, `docs/contracts/core-differential.md` CORE-06; §7).
- Message payload bound: `MAX_MESSAGE_PAYLOAD = 4,000,000` bytes (`crates/p2p/src/wire.rs`), Core's `MAX_PROTOCOL_MESSAGE_LENGTH`, on either transport. A v1 frame header declaring more is refused before its body is read, as Core does.
- Network magic and default ports come from `bitcoin_rs_primitives::Network` and are asserted equal to Core's constants per network (mainnet 8333, testnet3 18333, testnet4 48333, signet 38333, regtest 18444).
- `--p2p-magic` may override the message-start bytes on fork networks sharing a chain (a bitcoin-rs extension; requires `--network mainnet` semantics and explicit `--connect` peers). Not a Core option; recorded as extension, not parity.

## 4. Handshake Contract

An outbound connection sends, in order: `version`, `wtxidrelay` (BIP339), `sendaddrv2` (BIP155), `sendheaders` (BIP130). An inbound connection receives `version` and answers with the same four messages, then `verack` completes readiness (`crates/p2p/src/handshake.rs`, `dispatch.rs`).
BIP434 `feature` announcements, when any, follow those messages and precede `verack` on both roles, and go only to a peer whose `version` is `70017` or higher (`crates/p2p/src/feature.rs`, `handshake.rs`). Local announcements are disabled by default: `RelayOffers::stale_tip_relay` defaults off, so `Peer::stale_tip_offer` stays `None` and `negotiated_features` is empty. When enabled, `ConnectionShared::offer_relay_capabilities` calls `Peer::offer_stale_tip_relay` with the configured `stale_tip_prefers_blocks` byte, and `negotiated_features` emits one `BIP332` announcement carrying that byte (`crates/p2p/src/listener.rs`, `peer.rs`). `Peer::send` enforces the BIP434 send window: remote version ≥ `70017` must be known and our own `verack` must not have been successfully written; receiving the remote `verack` closes only the receive window. The post-handshake `PeerLease` queue refuses `feature` as a local caller error, cancels the lease, and releases reserved credit; it never turns this refusal into shared-budget backpressure.

The `version` message pins:

| Field | Value | Core 31.1 comparison |
| :--- | :--- | :--- |
| `version` | `70017` | deviation: Core 31.1 advertises `70016`. `70017` is the BIP434 negotiation threshold; `getnetworkinfo.protocolversion` reports the same `wire::PROTOCOL_VERSION`. The `version` field inside `getheaders` is rust-bitcoin's `70001`, not this value |
| `services` | `NETWORK \| WITNESS`, or `NETWORK_LIMITED \| WITNESS` when `storage.prune_target_mb > 0`; adds `P2P_V2` while `v2transport` is on (default) and `COMPACT_FILTERS` only when the optional filter index is ready | Core derives the base set from the prune setting (`init.cpp`): a pruned node never advertises `NODE_NETWORK`. `--blockfilterindex` defaults off and requires unpruned history. `BLOOM` remains unsupported |
| `relay` | `true` on a full-relay connection, `false` on a block-relay-only dial | matches Core's per-connection preference (`net_processing.cpp`) |
| `user_agent` | `/bitcoin-rs:<version>/` | distinct subver string; Core records it in `getpeerinfo.subver` |
| `timestamp` | `0` | deviation: no real clock is sent; Core 31 does not misbehave-score time offsets (live interop evidence), but this remains a recorded deviation |
| `start_height` | current applied tip height | matches Core semantics |

Rules, each enforced by the FSM (`crates/p2p/src/fsm.rs`) and identical to Core's posture unless noted:
- `verack` before `version` → disconnect. A duplicate `version`, including before readiness, is a typed handshake-ordering violation (§6): it does not replace the accepted version or its receive timestamp and does not replay negotiation responses. Protected connections ignore the violation under the existing handshake deadline.
- Any non-handshake message before readiness → disconnect. Core has the same rule except for a small handshake whitelist (`sendtxrcncl`); see §7 for the one practical divergence.
- After `verack`, unknown commands are ignored and the connection stays up (identical to Core).
- A `feature` message is accepted only after the peer's `version` and before its `verack`, and only from a peer that advertised `70017` or higher; otherwise it is a handshake-ordering violation (§6). A truncated payload, non-minimal `CompactSize`, identifier length outside 4–80 bytes, more than 512 data bytes, or trailing bytes is an invalid decoded payload (§6). Identifier bytes are otherwise unrestricted on receipt. Unknown identifiers, and invalid data for a recognised identifier, are ignored without disconnect. Only a recognised identifier with valid data is retained per peer; for a repeated identifier the first valid announcement wins; today the only such identifier is `BIP332` with a one-byte `0`/`1` payload. Identifiers this node advertises are limited to printable ASCII (`0x20..=0x7e`).

Outbound queue accounting. Every queued message is one charge of a message and its full wire bytes against two budgets: the connection's own (4,096 messages, 64 MiB) and the node's aggregate of queued outbound wire bytes, one strict 64 MiB cap shared by every connection of a `P2pService`, never process-global. The aggregate's pending total never exceeds its cap at any instant, with no empty-queue exemption; the connection's own caps admit a lone oversized message to an empty local queue, still charged to the aggregate. A bulk body reservation must also fit under the cap less one maximum frame, so control traffic flows while bodies are refused. A charge has one owner at every moment (reservation, then queued frame, then writer burst) and returns to both budgets exactly once when that owner drops (written, refused, discarded with the channel, drained on writer exit). A refused charge takes nothing and names its cause. The connection's own cap, or a returned writer, cancels the lease as before. The node aggregate is backpressure only: the lease stays live and the sender keeps its intent. Requests whose reply cannot be reserved (`ping`, `getheaders`, answerable `getaddr`, the `getblocktxn`/`getdata` follow-up to a `cmpctblock`/`blocktxn`) are deferred: the connection reads nothing until the reply can be reserved, dispatches once, never produces an unreserved reply. A probe `ping` and outbound `getaddr` stay owed until sent. Aggregate-refused time is a stall: not silence either direction for keepalive, not the age of a parked `getdata` tail or deferred request, not charged to a parked compact-filter request's five-second allowance. Local saturation, dead writer, and silence outside a stall keep their rules. Background producers keep intent when the aggregate refuses them: `getheaders`, block `getdata`, cold-start hedges are replanned next tick (hedge tries the next candidate); transaction `getdata` returns its claim to the request owner; refused `feefilter` restores its schedule; refused relay `inv` returns requests to the peer's pending queue; refused block announcement, `sendcmpct` demotion, or high-bandwidth rotation leaves the selection and retries.
Block serving resolves each body by its own `(height, hash)`, so stale and winning blocks at one height cannot be confused. Header-chain membership or `NodeStatus::Active` alone is not body-validation proof. Off-applied-chain `getdata` and deep `getblocktxn` fallback require the chain owner's recorded application count and, relative to the best header, timestamp age and proof-equivalent age strictly below 30 days (Core 31.1 `BlockRequestAllowed`, `net_processing.cpp`; shallow `getblocktxn` uses its separate stored-data path, `net_processing.cpp`). Bodies are parsed and hash-checked outside tree locks; eligibility and applied depth are rechecked after the read. Unknown, invalid, pruned, missing, malformed bodies are never forwarded. Unsolicited compact announcements retain their active-chain requirement. Already-stale branches whose application counts were not restored by a checkpoint stay ineligible until validation establishes that evidence; no persistent Core-style validation-status index is added.
Any command outside this table decodes as `Unknown` and follows §6, including the one Core 31 command absent above, `sendtxrcncl` (BIP330).
Transaction announcements target only connections with published handshake metadata. A `wtxidrelay` peer receives `MSG_WTX` with the accepted transaction's actual wtxid; other ready peers receive `MSG_TX` with its txid ([BIP339](https://github.com/bitcoin/bips/blob/master/bip-0339.mediawiki)). RPC/reorg mutation observers resolve the retained entry's wtxid and skip entries removed before delivery. Missing-parent requests use txids, which BIP339 permits for unannounced parents. `NODE_WITNESS` sources receive `MSG_WITNESS_TX` requests so the parent includes its witness; others receive `MSG_TX` ([BIP144](https://github.com/bitcoin/bips/blob/master/bip-0144.mediawiki#relay)). Relay-queue saturation drops the newest announcement without blocking admission; a connection's own outbound saturation cancels that connection's lease, while a full node aggregate only defers the send and cancels nothing. Each queued announcement is checked against the shared mempool immediately before its relay send, matched on the admission epoch recorded when queued: a transaction that left the pool, or was re-admitted under a new admission, is consumed with no `inv` (narrows, not closes, the stale-announcement window; a removal landing between check and send cannot be retracted). The inventory view respects the reject cache's identity scope: witness-only refusals suppress the exact wtxid, not legacy txid inventory or another witness variant. Cache and retry lifecycle are governed by [MPL-04](../contracts/mempool-mutations.md#mpl-04-generation-validated-admission-and-chain-change-fencing).

## 6. Message policy and automatic discouragement

The P2P service owns both the existing in-memory manual subnet bans and a separate bounded, process-local set of discouraged **exact IP addresses**. There is no additive score or second persisted ban database. `listbanned` and `clearbanned` describe only manual bans. An ordinary automatic peer's current connection records a typed remote protocol violation before teardown; an old lease cannot punish its same-address replacement. Local queue saturation, network inactivity, startup cancellation, insufficient advertised services, transport I/O/timeouts, and local encoding failures never discourage an IP.

| Condition | bitcoin-rs action for an ordinary automatic nonlocal peer | Core 31.1 reference |
| :--- | :--- | :--- |
| Unknown command after readiness | ignore | ignore |
| Decoded compact-filter requests with a non-basic type, unknown/unapplied stop, inverted range or more than 1,000 filters / 2,000 hashes | ignore and keep the connection open, without discouragement | `PrepareBlockFilterRequest` disconnects without discouragement; deliberate connection-policy deviation, tested by the compact-filter wire probe |
| Invalid handshake ordering | disconnect and temporarily avoid the IP | Core ignores some cases, including redundant `version` and messages before `version`; bitcoin-rs retains its stricter FSM |
| Invalid decoded payload or structural count (including a malformed `feature` payload) | disconnect and temporarily avoid the IP | Core's payload exceptions and individual handlers have distinct rules; not blanket parsing-error parity |
| Checksum failure | disconnect and temporarily avoid the IP | Core v1 rejects the message and resets its decoder; stricter bitcoin-rs policy |
| Wrong magic (including a BIP324 key read with v2 off) | close the unread transport, without discouragement | Core closes the transport on a wrong message start without `Misbehaving` |
| Invalid command bytes or length above 4,000,000 bytes | close the unread transport; temporarily avoid ordinary remote IPs | Core transport rejection, same 4,000,000-byte cap, separate from `Misbehaving` |
| `inv`/`getdata` above 50,000, `addr`/`addrv2` above 1,000, `headers` above 2,000 | disconnect and temporarily avoid the IP | the relevant Core handlers mark for discouragement |
| Locator above 101 or `notfound` above 50,000 | disconnect and temporarily avoid the IP | Core directly disconnects oversized locators; oversized `notfound` is ignored by request handling, without generic punishment |
| `getblocktxn` indexes beyond the body on the `blocktxn` serving path | disconnect and temporarily avoid the IP | Core marks these body-relative bounds violations for discouragement (`net_processing.cpp`), separately from differential decoding |
| Empty `getblocktxn` list or non-increasing in-process absolute indexes | disconnect and temporarily avoid the IP | Empty rejection is stricter native policy; Core accepts an empty list. Both wire decoders guarantee increasing indexes before lookup (`blockencodings.h`, `net_processing.cpp`). Core decodes `uint16_t` indexes; the native codec retains `u64` indexes, with different range acceptance |
| `tx` or transaction `inv` on a block-relay-only connection | disconnect without discouragement | connection-role rejection; not a new numeric penalty |
| `addr` or `addrv2` on a block-relay-only connection | ignore | address relay is declined |
| Idle connection | ping once a direction has been idle 2 minutes; disconnect once a direction is silent past 20 minutes, except receive silence does not count while a paused `getdata` stops the connection from reading; no discouragement | periodic ping and outstanding-ping timeout remain distinct from misconduct |
| Valid traffic exceeds local queue/request budgets | bounded accounting, backpressure or connection-local cancellation | resource management, not a generic punishment score |

Discouragement retains at most 4,096 canonical IPs for one monotonic hour. Repetition does not refresh the deadline or add another queue entry. At the capacity bound the oldest entry is evicted. Core instead uses a rolling Bloom filter with 50,000 elements and no explicit time expiry. Selection snapshots are captured before the address-book lock and applied to regular candidates, feelers and restart anchors. Inbound accepts and outbound socket admission recheck current policy, including after a queued dial connects.
Manual connections and operator-protected peers discard a fully consumed bad message and continue. An unread/unsafe frame still closes the transport without address discouragement, as do unrelated I/O and resource failures. Other local peers disconnect without recording their address. Locality follows Core's `CNetAddr::IsLocal`: IPv4 0/8 and 127/8, IPv6 `::1`; IPv4-mapped IPv6 is canonicalized before matching. Private LAN addresses are not implicitly local.
The optional `--p2p-noban <IP/CIDR,...>` setting (TOML `p2p_noban`, environment `BITCOIN_RS_P2P_NOBAN`) defaults to empty. The existing `IpSubnet` owner parses and normalizes it. Permission derives only from the actual socket IP, never from advertised addresses. `getpeerinfo.permissions` reports `noban` for these connections. This is an automatic-discouragement exemption, not Core's full permission framework: manual ban admission still wins; transaction relay, fee filters, resource budgets and connection roles are unchanged. No `Relay`, `ForceRelay`, `Addr` or generic permission flags are inferred.
References: pinned Core v31.1 [Misbehaving and exemption handling](https://github.com/bitcoin/bitcoin/blob/v31.1/src/net_processing.cpp), [rolling discouraged set](https://github.com/bitcoin/bitcoin/blob/v31.1/src/banman.h), [v1 checksum rejection](https://github.com/bitcoin/bitcoin/blob/v31.1/src/net.cpp), [canonical local-address classes](https://github.com/bitcoin/bitcoin/blob/v31.1/src/netaddress.cpp). The process comparison in `e2e/tests/peer_discouragement.rs` uses an oversized `headers` count, which reaches Core's `Misbehaving`, to test ordinary local disconnect/reconnect and operator `NoBan` survival via a ping/pong barrier.

## 7. Deviation Ledger

Known deltas from Core 31.1 (the `TXR-nn` labels index Core's tx-relay inventory in `net_processing.cpp`: TXR-01–07 are the per-peer request-tracker duties Core 31.1 owns in `node::TxDownloadManager` (`src/node/txdownloadman.h`), issued through `GetRequestsToSend` in `SendMessages` (`net_processing.cpp`); TXR-09 is the trickled inventory schedule, `m_next_inv_send_time` at `net_processing.cpp` under the `INVENTORY_BROADCAST_*` delays):
1. **BIP324 v2 transport**: on by default, as in Core 31. Live run against unmodified Core 31.1 recorded v2 in both directions with matching session ids, ping answers, and full header/block sync each way, plus a v2-off node syncing over v1 from v2 Core (https://github.com/gosuda/bitcoin-rs/pull/1612; CORE-06). No deviation known; the v1 retry after an unanswered v2 dial, decoy packets and rekeying rest on in-tree tests only. `--v2transport=false` keeps every connection on v1 and stops advertising `NODE_P2P_V2`. BIP324 does not authenticate peers, so it does not stop an active MITM or eclipsing peer.
2. **BIP330 `sendtxrcncl`**: not implemented; the one Core 31 command missing from the 42-command table. Decoded as `Unknown`: ignored from a ready peer (Core ignores unknown commands too), disconnected before readiness. Core whitelists it during handshake, so the only affected topology is a Core peer *dialing* bitcoin-rs with `-txreconciliation=1`. The supported topology (bitcoin-rs dials Core) never receives it, because Core sends `sendtxrcncl` to outbound peers only.
3. **Proactive block announcements**: implemented for newly committed active tips. Ready peers receive unsolicited BIP152 high-bandwidth compact blocks (up to 3 peers when parent is known and tx relay is active), BIP130 headers (up to 8 blocks when anchored to the active chain), or fallback single-block `inv` (`MSG_BLOCK`). Stale tips across reorgs are discarded; intermediate tips are coalesced under queue backpressure.
4. **Address management**: one P2P-owned `AddressBook` retains canonical endpoints, original source and health, and up to eight distinct New bucket references. IPv4-mapped IPv6 aliases are canonicalized at every book endpoint boundary; other linked IPv6 forms keep distinct endpoint identity, with only netgroup classification linking IPv4. Placement follows Core 31.1 `GetNewBucket`/`GetTriedBucket`/`GetBucketPosition` (SHA256d with the persisted 256-bit secret, Core vector framing, endpoint wire bytes, separate New/Tried position domains): 1,024 New and 256 Tried buckets of 64 positions; one source group reaches at most 64 New buckets, a destination group at most eight Tried buckets. IP grouping includes linked IPv4 /16, ordinary IPv6 /32, Hurricane Electric /36 and Core's local/unroutable group. New DNS sources use the first ten SHA256 bytes of the seed name as Core Internal identities. `AddSingle` ordering governs time/service updates, probabilistic additional references (1/2^existing-reference-count), and occupied-slot replacement. Gossip applies a two-hour time penalty except a source's self-announcement; DNS applies none. An IsTerrible incumbent or one redundant reference of a healthy multiply referenced incumbent may yield a New slot; clearing a slot removes one reference and only the final New reference deletes the endpoint. Local pending ownership protects final endpoint deletion, not every redundant slot. Success promotes to a vacant Tried slot and removes all New references. A Tried collision retains the newcomer in New and enters a runtime-only set of at most ten distinct challengers; runtime-only creation IDs preserve Core's collision ordering across record swaps; no ID or collision set is persisted. Core `ResolveCollisions` protects an incumbent successful within four hours; an attempt within four hours permits replacement only after more than 60 seconds, otherwise a challenger waiting more than 40 minutes can replace an untested incumbent. Exact boundaries use existing health timestamps. Replacement calls the same Good(false) transition, clears all challenger New references, demotes the incumbent to one original-source New reference; only the collided destination New reference is cleared. Pending final-reference victims defer the whole transition. Local active/manual/pending endpoints stay protected. Resolver snapshots cover at most twenty endpoints and run outside the state lock before rechecking current state. Collision choice samples the shared RNG; feeler scheduling uses Core's Poisson interval with a two-minute mean. Selecting an already TCP-connected incumbent records Good and falls back to the New-only sampler; queued/inflight work alone never certifies Good. Feeler targets require stored NETWORK or NETWORK_LIMITED. DNS records retain unknown service bits until a handshake supplies them. Ordinary selection, restart-anchor admission, automatic dispatch and the final pre-TCP check share one desirable-service predicate: NETWORK plus WITNESS, or LIMITED plus WITNESS while approximate local tip depth is below 144. Manual dials and feelers bypass this metadata prefilter. Accepted VERSION metadata overwrites the one stored service field before ordinary service rejection, without marking Good, changing health times or promoting membership: unknown DNS metadata is `None`, an observed zero-bit claim is `Some(0)`; gossip ORs bits into the same field and zero-bit gossip preserves an existing unknown; only genuine unknown DNS metadata can bootstrap ordinary selection; an accepted NONE VERSION is excluded immediately even without Good; a successful NONE feeler still remains Good/Tried but is excluded from ordinary dialing. Feelers finish on a valid VERSION through the native parser/FSM without readiness or sync work. Collision state starts empty after restart. The shared IsTerrible predicate first protects attempts within 60 seconds, then checks future timestamps beyond ten minutes, age over 30 days, three never-success failures, or ten failures with success older than seven days. No periodic age/failure purge; replacement cleanup happens at New-slot admission; fresh getaddr samples filter IsTerrible. Attempt health is recorded only after an actual TCP attempt. Local ban/activity/cancellation refusal and failed thread creation do not age a peer. Failures count only once per global Good epoch and only with Core's persistent-outbound-netgroup connectivity gate derived from `max_peer_connections`; established manual and handshaking outbound sessions count, inbound/transient feelers/cancelled sessions do not; manual attempts never count a failure or own an automatic claim. Good from any non-inbound handshake resets failures and records success/recent try for known peers (unknown manual peers are not inserted) without overwriting advertised last-seen time. Native periodic refresh applies only to ready automatic full-relay peers, excluding feelers, at intervals over 20 minutes; block-relay peers never refresh an advertised timestamp but still count for DNS recovery. Last-try/count-attempt/global-Good times are runtime-only. Selection chooses New/Tried once with equal probability when both are eligible, then samples a bucket and circular start position. Acceptance uses Core GetChance: 0.01 for attempts within ten minutes, multiplied by 0.66^min(failures,8), with a 1.2 factor after rejection; acceptance is guaranteed within 45 occupied proposals. Policy callbacks run outside the book lock; membership/health/pending constraints are evaluated after reacquisition. Endpoint exclusion includes inbound; whole-group exclusion uses outbound/pending only. Ingress rejects future (>10-minute) and older-than-30-day reports. Native port/routability admission is retained (`addrman.rs::routable`), including its narrower IPv6 ranges and reserved IPv4 exclusions. IP, Tor v3 and I2P destinations are supported. DNS remains bounded bootstrap input (64 results per seed pass), not a second address owner. Books with at least 64 records get 60 seconds to connect before a remaining ready-outbound deficit permits DNS recovery; smaller books query immediately; each path makes at most one seed pass per 60 seconds. Full-relay gossip allowance is 32 entries, replenished one per ten seconds. Getaddr is answered once per inbound full-relay connection, never outbound. Its shared at-most-32-entry sample stays byte-stable for 24 hours across reconnects/discoveries, then rotates and applies IsTerrible filtering. Tor v3 and I2P addrv2 families are retained; other non-IP families ignored; block-relay-only peers neither learn nor serve addresses. Fixed indexes occupy 327,680 bytes; endpoint count is bounded at 81,920 with at most eight New bucket IDs each and at most 65,536 occupied New slots. On the tested 64-bit target Candidate is 184 bytes and Source is 40 bytes, excluding allocator/index/vector overhead. Fixed-width serialized fields have a conservative 512-byte/record bound (315-byte max-width fixture), so separators plus bounded header/checksum stay below the 64 MiB file ceiling. Reads bound both bytes and record/reference sequences. `--asmap <file>` (TOML `asmap`, env `BITCOIN_RS_ASMAP`) loads one immutable classifier through the P2P netgroup owner; its validated Core bytecode is bounded at 4 MiB. Placement, source corroboration, outbound diversity and persistent-TCP failure counting use that map. Core ASN groups serialize as NET_IPV6 plus little-endian ASN bytes, grouping IPv4/IPv6 together. ASN0 uses the corrected prefix/HE fallback; public linked-IPv4 forms use embedded IPv4 without rewriting the dial endpoint. Internal DNS sources retain their source namespace. Startup logs the raw-file SHA256 identity. Invalid/unavailable maps permit memory-only prefix fallback but disable all book publication and incompatible-file preservation; restoring the map recovers the untouched book. Intentionally changing or omitting a map rebuckets the current format, prioritizing proven/recent successes and logging retained/demoted/dropped counts. Anchors are pruned only when their endpoint is removed. Same-map restart retains every reference. AddrMan reads/writes one canonical checksummed JSON snapshot with `format: "bitcoin-rs-addrman"` and `version: 1`. `SCHEMA_VERSION` MUST remain `1` until the first official bitcoin-rs release; before that release, edit this definition directly: do not add compatibility readers or increment the version; only after release may a breaking change increment the version with an explicit compatibility decision. The canonical object has `format`, `version`, `magic` (four P2P magic bytes), `secret` (32 bytes), `records`, `asmap_id` (null or 32 bytes), `anchors`; trailing 32 bytes are SHA256 of the exact UTF-8 JSON payload. Endpoint strings are IP sockets, Tor-v3 host:port or I2P host:port; mapped IPv4 canonicalizes to IPv4. Each record has `addr`, `services`, `source`, `last_seen`, `last_success`, `failures`, `tried`, `new_buckets`. Source is exactly one of `{"ip": <IP>}`, `{"overlay": <onion/I2P address>}`, `{"internal": <10 SHA256 seed-hash bytes>}`; overlay sources cannot contain IP or ephemeral handles. Each anchor is `{"addr": <endpoint>, "confirmed_at": <Unix seconds>}` naming a unique successful record, at most two anchors. Runtime attempt/count-attempt/global-Good times and creation IDs are not persisted. Services is required: JSON null means unknown DNS metadata (valid only for an Internal source with no prior Good), numeric zero means a known zero-bit claim. Unknown fields, invalid membership, unsafe endpoints, malformed anchors, or excessive sizes fail closed. Tor/I2P endpoint hash keys use BIP155 tags 4/5 plus 32 identity bytes and big-endian port; netgroups are `[4, key[0] \| 15]` / `[5, hash[0] \| 15]`; internal source groups use tag 6 plus ten seed-hash bytes; ASMap applies to IP only. Unmarked pre-release v1-v9 files are never decoded or migrated; only their bounded JSON envelope, checksum and network identity are checked. Before replacing one with an empty/freshly seeded canonical book, its exact bytes are exclusively published and file/directory-synced to `.pre-release-<sha256>.bak`; a pre-existing backup is reusable only if a regular file with identical bytes flushed successfully; preservation failure disables replacement; the original stays at its source path until atomic save succeeds. No old peers, secrets, health or anchors are imported. Filenames stay scoped to actual P2P magic: `peers.dat` becomes `peers-<8 hexadecimal magic digits>.dat`. A valid scoped book wins; a same-magic unscoped current book may be copied into the scoped path unaltered; a valid foreign-magic base is left untouched. Corrupt/unknown/unreadable files disable publication while in-memory discovery continues. Publication retains exclusive random temporary creation with bounded collisions, file sync, atomic installation and the storage owner's directory-sync policy. First installation cannot overwrite a newly appeared destination. Saves retain the captured revision only after durable success, outside the state lock. Periodic saves occur every 15 minutes; shutdown/explicit barriers are immediate. Restart anchors come only from automatic block-relay peers that supplied accepted chain evidence, with the seven-day age limit; on the first active-network maintenance tick they are removed from the durable snapshot before any endpoint is exposed for dialing. Failed/read-only publication exposes no anchors. Confirmation metadata moves into the pending reservation; queued reservations consume a normal outbound slot, feelers do not. Accepted worker dispatch consumes an anchor at most once; never-dispatched reservations return before shutdown save with the original confirmation time; dispatched attempts never return merely because connection fails. A stale queue item cannot dispatch after its reservation was returned. Actual Core group/placement evidence includes 224 ASMap rows and official Tried236/New795 anchors; current-format tests retain IP/Tor/I2P round trips, anchors, membership, services, map changes and atomic publication proofs: specific algorithm/persistence checks, not full peer-lifecycle parity. No historical migration fixtures exist.
5. **Service bits**: base set follows storage (`init.cpp`): `NETWORK \| WITNESS` normally, `NETWORK_LIMITED \| WITNESS` when `storage.prune_target_mb > 0`, so a pruned node never claims full history. `NODE_P2P_V2` added while `v2transport` is on (default), as Core does. `NODE_BLOOM` unsupported. `NODE_COMPACT_FILTERS` advertised on new handshakes only while the explicitly enabled filter index is healthy and caught up. Pruning and filter indexing cannot both be enabled. Existing connections keep negotiated flags, but each filter query checks current readiness (see [the indexing contract](../contracts/indexing.md) and [the pinned Core/Kyoto runner](../../tools/compact-filter-interop/README.md)).
6. **Timestamp**: `version.timestamp` is always 0 (§4).
7. **Automatic discouragement** (§6) uses bounded exact-IP expiry rather than Core's rolling Bloom filter. Explicit strict-parser, transport and permission differences are listed in §6; there is no additive score.
8. **Chain-sync timeout scope**: a full-relay outbound connection that stops bringing a better chain is timed out as Core does (`ConsiderEviction`, `net_processing.cpp`), with one `getheaders` probe at 20 minutes (`CHAIN_SYNC_TIMEOUT`, `net_processing.cpp`) and the first four outbound connections to reach the tip protected (`MAX_OUTBOUND_PEERS_TO_PROTECT_FROM_DISCONNECT`, `net_processing.cpp`). Protection and timeout both key on a tip the peer actually handed us, never the handshake-claimed height: Core reads `pindexBestKnownBlock`, not `nStartingHeight` (`net_processing.cpp`). Operator-pinned connections are exempt in both, as in Core (`IsOutboundOrBlockRelayConn()` excludes `ConnectionType::MANUAL`, `net_processing.cpp`). Block-relay-only connections are exempt here; Core times out both outbound classes.
9. **Download budgets**: one sync is bounded at `PENDING_BUDGET = 256` in-flight and `RECEIVED_BLOCK_BUDGET = 256` staged bodies (`crates/p2p/src/download_window/policy.rs`), striped at `MAX_BLOCKS_IN_TRANSIT_PER_PEER = 16` once `MIN_PEERS_FOR_FANOUT = 8` eligible peers exist, where Core runs one `BLOCK_DOWNLOAD_WINDOW = 1024` ahead of the last common block with the same 16 per peer (`net_processing.cpp`). The 256 depth is measured: a bounded 0–150,000 daemon single-peer IBD run at this window was 1.52× the 128-block control (`policy.rs`). The shallower window is a bounded divergence kept by operator decision.
10. **Extra-peer selection**: once a stale tip needs no extra full-relay connection, the newest automatic full-relay outbound connection one beyond the slots and older than `MINIMUM_CONNECT_TIME` is retired (`retire_extra_full_relay_connection`, `crates/p2p/src/service.rs`). Operator-pinned connections are outside the count and victim set, as in Core (neither `IsFullOutboundConn()` nor `IsBlockOnlyConn()` includes `ConnectionType::MANUAL`, `net_processing.cpp`). Core's `EvictExtraOutboundPeers` (`net_processing.cpp`) instead retires the connection that announced a block longest ago, tie-broken by dropping the most recently connected one. The retired count is the same; the retired connection is not.
11. **Unanswered ping**: Core sends one ping per `PING_INTERVAL`, remembers the nonce, and ends the connection when the pong has not arrived by `TIMEOUT_INTERVAL` after that ping regardless of other traffic (`net_processing.cpp`). bitcoin-rs probes on the same cadence and ends a connection when either direction is silent for `TIMEOUT_INTERVAL`, but credits any inbound message as receive activity and keeps no outstanding-ping record, so a peer that never answers a probe while other traffic continues is not retired by this rule here.
12. **Inbound eviction**: once live inbound count reaches `max_peer_connections - outbound_full_relay_slots - outbound_block_relay_slots` (default `200 - 8 - 2 = 190`, Core `net.h`), a newcomer at an address holding a live inbound connection replaces it without eviction. Any other newcomer evicts the connection chosen by a port of Core's `SelectNodeToEvict` (`node/eviction.cpp`), or is refused when every candidate is protected or its address holds a live outbound connection (`crates/p2p/src/eviction.rs`, `PeerTable::try_register_inbound`; Core `net.cpp`). The port differs from Core as follows, so its choice can differ: no minimum-ping protection (Core protects the eight lowest-ping connections; none are measured here, item 11); recency is an order, not a clock (Core compares whole-second times, same-second ties fall through; here delivery sequence and monotonic instant order); a block counts once applied (Core credits newly stored blocks including side branches, `net_processing.cpp); wanted services are judged at eviction (Core fixes `fRelevantServices` at `version` arrival, `net_processing.cpp`; here `has_all_desirable_service_flags` is evaluated against tip depth at the newcomer's arrival, differing only for a `NODE_NETWORK_LIMITED` peer crossing the 144-block threshold in between); a newcomer at an address holding a live outbound connection is refused instead of evicting (one connection per address; Core keeps both); uptime protection is reserved for localhost only, even with overlay transports enabled (Core reserves part for onion, I2P, CJDNS and localhost). Two Core steps never apply: BIP37 filters are ignored, so no peer has the bloom filter Core's transaction-time tie-break looks at; a discouraged address is refused at accept, where Core admits it while inbound slots are not almost full and evicts it first (`net.cpp`).
13. **Outbound service gate**: an outbound peer not advertising the desirable set is disconnected right after its `version`, before publication as usable, exactly as Core's `HasAllDesirableServiceFlags` check (`net_processing.cpp`). Desirable set is `NETWORK \| WITNESS`, or `NETWORK_LIMITED \| WITNESS` while the local tip is younger than 144 blocks (`NODE_NETWORK_LIMITED_ALLOW_CONN_BLOCKS`). Inbound peers are not service-checked, as in Core.
14. **Limited peers and block download**: a connection without `NODE_NETWORK` is never asked for block bodies while in IBD, and after it only for the last 288 blocks of that peer's own chain (`net_processing.cpp`, `NODE_NETWORK_LIMITED_MIN_BLOCKS`). The rule reads the node's single `InitialBlockDownload` latch and applies to request, fan-out, probe, and hedge selection alike; header requests stay open to such a peer.
15. **Transaction download scheduling bounds**: one P2P owner tracks txid and wtxid announcements: 5,000 retained announcements and 100 in-flight requests per connection, 60-second request lifetime, two-second non-preferred / txid-while-wtxid-peers-exist / overloaded-source delays (Core `node/txdownloadman_impl.cpp`). Outbound eligible sources win over inbound. Matching `notfound`, disconnect and expiry release ownership and make remaining announcers immediately eligible; unsolicited `notfound` cannot release another source's request. Admission completion releases only the delivering source; alternate witnesses stay eligible until mempool/orphan/reject state retires the matching identity; accepted bodies retire both identities. A paced 100-ms pass checks at most 1,024 retained and 1,024 ready identities before sending. The ordered request owner supplies resumable cursors for sweeps and ready batches, so reannounced lower keys cannot starve older tail requests. Gateway reads happen without policy/table locks; candidates are rechecked before reserving under one owner lock. Only transaction `inv` wakes periodic policy work; ping/headers/unrelated traffic perform no gateway census. Matching notfound/disconnect/admission results use scoped immediate checks. TX/WTX announcements with identical 32-byte hashes share one download ownership domain, including source preference and failure fallback (Core `txrequest.cpp` `ByPeer`/`ByTxHash`); known/reject checks retain inventory type. Different raw hashes stay independent until a body proves their txid/wtxid relationship; no persistent alias map or second body cache. Native resource policy adds: at most 100,000 total announcements and eight sources per raw 32-byte hash shared by TX/WTX; at either limit a preferred arrival may replace one non-preferred, non-owner candidate with the largest numeric priority (a full hash must replace within that hash; that removal also frees a global slot when both caps are full); current owners and preferred candidates are protected; ordinary arrivals or fully protected limits are refused, as are duplicates and sources already at their 5,000-entry cap, without eviction or punishment. One derived ordered set holds at most 100,000 fixed-size references (priority, typed identity, connection ID). Global victim selection uses the ordered index with logarithmic updates. Orphan-parent requests share the owner and limits but keep immediate source retry rather than Core's parent delay; a parent already announced by that source is expedited without another announcement or second in-flight owner; ordinary duplicate `inv` cannot bypass its delay. These hard caps are resource-policy bounds, not measured throughput claims.
16. **Inventory timing and bounds** (TXR-09): transaction identities are queued under the same P2P owner as downloads. Inbound connections share an exponential deadline by remote IP network class and actual local bind IP/port, matching Core's key for supported IP transports; outbound connections have independent deadlines. Deadlines use Core's 5-second inbound and 2-second outbound means, plus a 30-second maximum delay. During IBD, due ticks advance the deadline without draining pending inventory. Outside IBD, each due tick orders queued parents before children and prefers higher-fee eligible entries, then sends at most `min(1000, 70 + 5 * (pending / 1000))` vectors, matching Core's target and cap. Empty ticks also advance the deadline. Additional bounds: 5,000 pending entries per peer and 100,000 globally; overflow drops new entries without blocking admission or discouraging peers. Each connection remembers 5,000 exact recently known identities in a bounded FIFO set (Core uses a rolling Bloom filter). `relay=false`, block-relay roles, source exclusion, negotiated txid/wtxid encoding, latest fee filter, and queued admission epoch are rechecked at their owning boundaries.
17. **Outgoing fee-filter timing**: the threshold comes from the gateway's mempool-pressure/min-relay projection, rounded through Core v31.1's 1.1-spaced grid (50 sat/kvB initial boundary, 10,000,000 sat/kvB maximum grid), floored at the configured min-relay. Unchanged values are not resent; randomized refreshes average ten minutes. A substantial change advances a distant refresh to within five minutes. IBD uses the high filter; exit schedules an immediate floor refresh. The extra inventory latency cap and exact known-inventory FIFO are bounded-resource choices; no throughput or bit-for-bit timing parity is claimed.
18. **BIP434 `feature` negotiation and BIP332 stale-tip relay**: implemented against the draft specifications (`crates/p2p/src/feature.rs`, `staletip.rs`), default-off opt-in (`RelayOffers::stale_tip_relay`, `crates/p2p/src/listener.rs`, `service.rs`). An enabled node offers one `BIP332` announcement with its `stale_tip_prefers_blocks` byte to peers ≥ `70017` and records the peer's `BIP332` byte only when it offered; either direction additionally requires the peer's `BIP332` negotiation and inactive IBD (§5). Core 31.1 does not support BIP434 and advertises `70016`, so bitcoin-rs never sends it a `feature` message; no Core 31.1 interop or support is claimed and that leg is blocked until a BIP434-implementing Core build is pinned (§2.1).

- **Live lane (cut)**: owned by [`CORE-01` / `CORE-02` / `CORE-03` / `CORE-05` / `CORE-06`](../contracts/core-differential.md). `CORE-05` compares outbound `inv`, `headers`, and high-bandwidth `cmpctblock` frames from equivalent peers on pinned Core and bitcoin-rs, including a live reorg. `CORE-06` runs BIP324 v2 against Core in both directions. This policy does not restate the Core version, RPC set, or CI job. Node-level reorg effects are coordinated in `crates/node/src/reorg.rs` (`switch_to_branch`, `invalidate_block`); the reorg fixture pins the peer-visible part at the `ChainQuery` seam via `reorg_switches_which_chain_a_peer_sees` (`crates/p2p/tests/core_compat.rs`). ## Overlay transports

`primitives::endpoint` owns logical IP, Tor v3 and I2P destination identities, keying the peer table, connection sources, mempool attribution, address book, netgroups and relay. A loopback SOCKS/SAM hop is never the remote peer's identity. The existing listener owns Bitcoin framing, handshake, leases, counters, admission and message processing for all streams. `p2p::overlay` owns opt-in route selection and SOCKS5/SAM setup; its private Tor control and IVNP SAM workers join `P2pService` startup/shutdown. The service, transport and admission share one immutable routing configuration. The SAM session owns its local destination; RPC advertises it only while that session is live and inbound acceptance is enabled. Allowed-network policy is checked at selection and final admission. [Configuration reference](../getting-started.md#tor-and-ivnp-i2p-networking) owns option spellings and defaults. Setup uses absolute deadlines and bounded cancellation polls for local overlay-service I/O. Direct IP dialing keeps the single 10-second TCP connect timeout and does not poll cancellation during that call. SAM session preparation has a 120-second bound; onion-circuit and I2P-stream connection have a 60-second bound. Local service errors never enter remote discouragement nor count as failed overlay peer attempts. Explicit SOCKS destination-unreachable/refused replies and SAM stream `CANT_REACH_PEER`/`TIMEOUT` replies, plus SAM naming `KEY_NOT_FOUND` while dialing, update address-book attempt/retry policy; undocumented naming results (including `TIMEOUT`), authentication, malformed replies, local I/O and control-session failures stay local errors. The existing outbound drain owns one retry policy for all `--connect` and persistent `addnode` destinations (direct IP, SOCKS, SAM): the fixed-peer worker only resolves names and publishes desired destinations, never schedules a connection. The drain canonicalizes pins, keeps at most one active dial per endpoint, waits 1–60 seconds after completion or local admission refusal before retrying; observing a ready connection resets backoff; removing a pin removes its retry state; one-shot manual requests create no retained retry state. `run_sam` alone publishes/removes the SAM session record and starts replacement epochs, each with one irreversible liveness marker shared by its streams and leases. Control-session loss or `INVALID_ID` revokes only the observed marker; a late failure cannot revoke the replacement. Reads, including mid-payload reads, use `PeerLease::is_cancelled` (local cancellation plus that epoch marker). The SAM worker asks the peer table to wake only leases carrying its exact epoch marker. The SAM worker restores the selected stable destination with bounded backoff. Inbound Tor identity is persistent but remote circuit identity is unknown: opaque per-connection handles disconnect a live connection but are never persisted, learned as address-book sources, or advertised as destinations. Inbound I2P uses `STREAM ACCEPT` Destination and port metadata. Both use ordinary inbound capacity/eviction with no localhost exemptions; Core's special onion/I2P uptime protection remains a deviation (§7, item 12). Inbound transaction-inventory clocks use remote network class and local bind endpoint; Tor circuits to one service share its bind clock; accepted I2P SAM streams have ephemeral local bind ports, so their clocks are per-stream. This differs from Core's shared inbound clock policy. Routable `PeerAddress`/`PeerEndpoint` values contain only IP, Tor-v3 and I2P destinations. Anonymous Tor circuits live in the connection owner's `PeerRemote`, keyed by lease connection id, sharing one unknown-origin admission group with no proxy-loopback protection and no destination to learn, persist, discourage or advertise; their RPC handle is `tor-inbound-N:0`, accepted by `disconnectnode`'s address form but not by destination configuration or dialing APIs. AddrMan endpoint/source persistence follows the canonical v1 definition in §7; application keys use a separate versioned, checksummed create-once format; a bad existing identity fails startup and is never replaced. Local fixtures in `p2p::overlay` prove protocol transitions, refusal, malformed input, timeout/cancellation, service loss and key preservation, not privacy or external router interop. The manual [`overlay-interoperability`](../../.github/workflows/overlay-interop.yml) workflow runs `e2e/tests/overlay_connectivity.rs` against external Tor and the IVNP revision owned by [`scripts/overlay-interop.py`](../../scripts/overlay-interop.py); artifacts record executable hashes, peer identity/counters, headers/block exchange and stable service-address restart observations. A failing or absent campaign is unavailable evidence, not an advertised pass.
