# Current datadir format policy
`bitcoin-rs` supports exactly one persistent datadir format for authoritative chainstate bytes. It does not migrate, translate, or silently recover incompatible state. A schema change increments `CURRENT_SCHEMA`; the operator moves to a separately named datadir by fresh replay, or by an optional epoch-specific offline tool when one is offered. Format breaks are permitted redesigns, not defects; operator data safety is the invariant.
## CURRENT_SCHEMA scope
`CURRENT_SCHEMA` covers only authoritative chainstate bytes: the durable head, the coin set, body and undo extents and references, and identity metadata. Owner-local state (fee estimator, peer discovery, mempool snapshots, index layouts) carries its own versions and never moves this marker. The current epoch is `6`. The marker is written and synced before any authoritative store opens (contents synced everywhere; the directory synced where the primitive exists). The node never deletes user data automatically. Network/backend datadir ownership and multi-process locking are configuration and lifecycle concerns outside this marker (tracked in issue #242).
| Datadir state | Startup action |
| --- | --- |
| Empty directory | Create and sync the current epoch, then initialize the current schema |
| Marker matches current epoch | Continue startup (no durable head yet starts cold) |
| Missing marker (implicit epoch `0`), malformed marker, other epoch, or head referencing missing/corrupt bytes | Refuse open with `incompatible_schema`; never open, convert, reset, or repair in place |
## Operator resync procedure
1. Stop the node on the old datadir. Keep the old datadir untouched; incompatible code never opens it.
2. Create a separately named datadir for the new schema epoch.
3. Replay the chain from the network (or an explicit archive/reindex input) with the new binary.
4. Verify identity before use: pinned stop identity (height, block hash), durable head hash, and recorded body/undo digests.
5. Body, undo, and metadata bytes and their directories are fsynced before the durable head commits.
6. Switch the manifest to the new store atomically; the switch touches the new store only.
The durable head is the only commit point. Body and undo frames are appended and synced. Then one atomic named-family batch commits the head, undo rows, coin replacements, and metadata. Coins live in the engine `coins` keyspace (`ColumnFamily::Coins`) and are part of that batch. No journal and no periodic coin export carries them. Crash residue is ignored: file length and valid frames never promote a head. An unresolved batch resolves to the prior or the wholly proposed root, never a mix. The offline conversion tool `tools/storage-convert` (`bitcoin-rs-storage-convert --from <old-datadir> --to <new-datadir> [--to-engine rocksdb|surrealkv|mdbx] [--pool-from <old-pool-datadir> --pool-to <new-pool-datadir>]`) requires offline, quiescent source roots and exclusive access to distinct target roots. Storage SDKs accept ambient filesystem paths for internal database operations and background threads. The operator MUST stop all node processes before conversion. The operator MUST prevent other processes from modifying either tree or replacing any path component during conversion. The tool MUST read without mutating the source. It refuses a non-empty `--to` and never writes under `--from`. For each namespace, directory bytes are copied to `<to>/.convert-src/<ns>/` and opened from the copy; the source is never opened by an engine. The tool copies rows in ascending key order through `write_durable` (ordinary batches target 64 MiB while keeping valid large rows indivisible) and verifies per-family SHA-256 digests over `len(key) || key || len(value) || value` on both source copy and destination before step-specific transformations. The epoch 3, epoch 4, and epoch 5 runs recode the `UndoData` family per row from undo format version 1 to version 2; the destination digest covers the new bytes and its row count MUST equal the source row count. Checkpoint and archive handling depends on the step: `2 -> 3` copies the checkpoint roots and the `assumeutxo/` archive byte-for-byte, `3 -> 6` publishes a converted checkpoint and rewrites historical generations, and `4 -> 6`, `5 -> 6`, and `6 -> 6` convert each generation's engine image as specified below. No run that targets epoch `6` copies the retired `assumeutxo/` archive. It copies the remaining engine-independent files byte-for-byte (`blocks/`, `peers.dat`, network-scoped `peers-<magic>.dat` address books, `mempool-snapshot.dat`, and `fee-estimator-history.dat`; skipping `.lock`, `process-epoch*`, `.CURRENT_SCHEMA.tmp`, and unknown files). Journal inclusion depends on the source epoch: only an epoch 2 source copies `chainstate-journal/`; epoch 3, epoch 4, and epoch 5 sources omit it. The implemented routes are `2 -> 3`, the chained epoch 3, epoch 4, and epoch 5 runs that target epoch `6` (the epoch 5 route is the `5 -> 6` step below), and `6 -> 6` for an engine change on an epoch 6 source; the conversion does not take an epoch 2 source directly to a later epoch. An epoch 2 source therefore needs two invocations with distinct empty destinations: first `--from <epoch-2> --to <epoch-3>`, then a second run from that intermediate directory that chains to epoch `6`. Inspect the first verification report before using its destination as the second source; do not start the current node on the intermediate epoch 3 directory. The tool removes scratch and writes `<to>/CURRENT_SCHEMA` with the step's target epoch last (temp file, fsync, rename, dir fsync): `3\n` for `2 -> 3`, and `6\n` for every run that targets epoch `6`. It prints a JSON verification report covering copied namespaces, row counts, digests, and file sizes. Report write or flush failure MUST produce a failed exit; because conversion may already be published on disk, the operator MUST inspect the target rather than assuming rollback. Fresh replay remains the fallback. Cutover is an explicit operator action on the tool's verification report.

## Epoch 5 to 6 conversion

Epoch 6 is the current epoch. The current binary refuses an epoch 5 datadir. Convert it offline with `tools/storage-convert`. The conversion writes a new datadir. It never changes the source.

The `5 -> 6` step runs these actions in order:
1. It copies the `chainstate`, `txindex`, and `ledger` namespaces into the target engine. Every family except `UndoData` uses the same per-family digest checks as every conversion. It copies `blocks/` and the engine-independent files byte-for-byte. The retired `assumeutxo/` snapshot archive is never copied.
2. It recodes every `UndoData` row per key. It reads the undo key hash, decodes the source row with the retained version 1 decoder, re-encodes the spent coins with the version 2 encoder, and writes the new row to the target. The version 2 record holds only spent coins. The node derives created outputs from block bytes. The destination `UndoData` digest covers the new bytes. The row count MUST equal the source row count.
3. It converts every generation's engine image under `chainstate-checkpoints/` and `assumeutxo-historical-checkpoints/` to the target engine, including the version 1 to version 2 undo recode. It recomputes engine commitments and manifest digests, then rebinds historical head references and `CURRENT` before snapshot finalization. It reads the converted durable head. When the head names no snapshot base (`Uninitialized`, or a `Failed` anchor the node refuses to open), the step performs no snapshot work.
4. When the head names a snapshot base, the step resolves the compiled trust anchor for that height and hash. An unrecognized base stops the conversion with a typed error.
5. When the copied checkpoints hold a checkpoint the snapshot base resumes from (base on the checkpoint ancestry, with the pinned coin hash and transaction count when the checkpoint sits at the base), the step keeps it and drops the archive. The report sets `published_checkpoint` to `false`.
6. Otherwise the head must sit exactly at the snapshot base; a head above the base with no compatible checkpoint stops the conversion with `MissingCheckpoint` and names resync. The step verifies the retired archive from the source: `headers.dat` must hold exactly the pinned heights with linkage and proof of work, and `coins.dat` must stream to the pinned height, hash, and `hash_serialized` commitment. A failure stops the conversion with `SnapshotArchiveInvalid` and writes no marker. The step then publishes a checkpoint generation at the base from the converted engine coins, with the verified header tree and a coin scan that must equal the pinned commitment, and writes `CURRENT` last.
7. It carries the full-revalidation marker when present, removes scratch, and writes `<to>/CURRENT_SCHEMA` as `6\n` last.

The node resumes from the published checkpoint engine and the durable head without replaying from genesis. The published coin statistics are the node's own local scan of the converted coins, cross-checked against the pinned commitment during publication, and carry no external verification claim.

Epoch 5 is retired. Epoch 5 sources convert through the `5 -> 6` step above: their namespaces and checkpoint generation images convert with the undo recode, the retired `assumeutxo/` archive is not copied, and the run writes marker `6`. Epoch 4 sources convert through `4 -> 6`: their namespaces convert with the undo recode, each checkpoint generation's engine image converts to the target engine, and the run writes marker `6`. Epoch 3 sources convert through the `3 -> 4` actions chained with the snapshot finalization and the `5 -> 6` undo recode and write marker `6`.

For `4 -> 6`, `5 -> 6`, and `6 -> 6`, the converter MUST convert each generation's `chainstate/` engine image under `chainstate-checkpoints/` and `assumeutxo-historical-checkpoints/` to the target backend. It MUST preserve the logical generation identity and the headers and coinstats artifacts. It MUST recompute the manifest's engine artifact from the completed destination image and preserve all other manifest fields. It MUST compute the rewritten manifest's digest and rebind the selected `CURRENT` and any durable-head historical checkpoint references to that digest. Before each rebind, it MUST match the reference to the exact authenticated source identity: checkpoint root, generation, and manifest digest. An unmatched reference MUST stop conversion. The converter MUST leave the source unchanged. It MUST verify each image's family row counts and digests before schema publication. It MUST sync all target image files, rewritten manifests, new bindings, and their directories before final `CURRENT_SCHEMA` publication. A generation without an engine image MUST remain without one. The report MUST identify each converted image by its checkpoint root and generation.

## Epoch 3 to 4 conversion

Epoch 4 is retired. The `3 -> 4` step remains in the tool for epoch 3 sources: it performs the `3 -> 4` actions below, then the snapshot finalization, then the `5 -> 6` undo recode, and writes marker `6`. Its report reads `source_epoch: 3, target_epoch: 6`.

The `3 -> 4` step runs these actions in order:
1. It selects the current checkpoint generation under `chainstate-checkpoints/` and verifies its manifest SHA-256 against the `CURRENT` reference. A missing or invalid generation stops the conversion.
2. It reads the retired `utxo-v4.dat` artifact of that generation with the retained v4 reader. It sorts the coins by txid and bulk-ingests them into the engine `coins` keyspace.
3. It reads the durable head from the converted store. The head height MUST be at or above the checkpoint height.
4. It replays each height from the checkpoint height plus one through the durable head height. It reads block bodies and version 2 undo rows for each height. A missing body or undo row stops the conversion with `MissingBlockData` for that height. The copied undo rows are recoded from version 1 to version 2 before replay.
5. It normalizes the retired BIP30 overwrite undo rows, scans the destination coins, and requires their statistics to agree with the replay and durable head. It recomputes the `coins` family digest and the recoded `UndoData` digest for the verification report, publishes the converted checkpoint described below, and carries any legacy full-revalidation marker.
6. It writes `<to>/CURRENT_SCHEMA` as `6\n` last.

An epoch 4 datadir has no chainstate journal. The node writes no `chainstate-journal/` directory, and the `3 -> 4` step does not create one. That step reads a legacy `chainstate-journal/` only to carry a leftover full-revalidation marker to the target root; it does not clear the source marker.

The `3 -> 4` conversion does not copy `chainstate-checkpoints/`. It reads the selected source generation and publishes an engine-backed generation in the target (see Publication below). Epoch 4 coin state comes only from the `coins` keyspace. Its checkpoints contain a `chainstate/` engine image and no `utxo` artifact.

The `3 -> 4` run carries `chainstate-journal/full-revalidation` to `<to>/full-revalidation` when the source has it. The `4 -> 6` and `5 -> 6` runs carry an existing root-level `full-revalidation` marker to the target root, and fall back to the journal marker when the root has none. The `6 -> 6` engine-copy run also carries the root marker. These paths reject a marker larger than 9 bytes, preserve its bytes, fsync the copy and target directory, and write it before `CURRENT_SCHEMA`. The report lists it under `carried_markers`. A carried root marker still forces full revalidation from cold.

Each epoch-3 `assumeutxo-historical-checkpoints/gen-*` generation that has a `utxo-v4.dat` also gets a `chainstate/` engine image written from that file, with the coins in the `coins` keyspace. In the target generation, the converter rewrites the manifest without a `utxo` artifact, fsyncs it, removes `utxo-v4.dat`, and syncs the generation directory. It rebinds the target historical `CURRENT` and any validating durable-head checkpoint reference to the rewritten manifest digest only after matching the original source reference; an unmatched reference stops conversion. The target manifest is changed and the retired payload is removed; the source generation and its references remain untouched.

Publication. When the durable head equals the newest source checkpoint, the `3 -> 4` step publishes an epoch 4 checkpoint generation under `chainstate-checkpoints/`. It copies the source headers and coinstats artifacts byte-for-byte, writes a manifest with no `utxo` artifact, captures the converted chainstate engine as `chainstate/`, and writes `CURRENT` last. When the durable head is above the checkpoint, the step publishes a generation through the node's own checkpoint publisher. The header tree is the source checkpoint's tree extended with the replayed suffix headers, each checked for proof of work, prev-hash linkage, and the contextual header rules; a failure stops the conversion with a typed error. Its coinstats are the scan of the converted `coins` keyspace at the durable head, and the step requires that scan to agree with the replayed stats (count, amount, MuHash, and chain_tx_count) before it publishes; a mismatch stops the conversion before any `CURRENT` is written. These coinstats are the node's own local computation, the same kind every node checkpoint carries; they are not an external or AssumeUTXO commitment. The target generation replaces the source checkpoint as the resume point without copying the retired generation into the target. The report sets `published_checkpoint` to `true` in both cases, and the node resumes from the checkpoint engine and the durable head without replaying from genesis unless a full-revalidation marker requires a cold start.

Equal-head publication streams authenticated headers and coinstats through a fixed 16 KiB buffer, including valid header artifacts larger than 64 MiB. Each artifact's length and SHA-256 must match the source manifest before its temporary target file is synced, atomically renamed, and its directory synced. Artifact size does not introduce an additional whole-file publication limit; the canonical checkpoint validation bounds still apply. `CURRENT` remains the final checkpoint selection point.

## Owner-local versions and degrade behavior
Authoritative startup never fails because of an owner-local version; rejected artifacts are preserved and quarantined, never silently deleted. Fee estimator state degrades to insufficient-data status (never a fabricated rate or confidence). Peer discovery is the canonical AddrMan v1 per [P2P compatibility section 7](p2p-compatibility.md#7-deviation-ledger). Schema version 1 remains until first release. Unmarked development snapshots are preserved byte-for-byte, never migrated; corrupt files disable replacement while startup continues. Mempool snapshots carry a mempool-owned version, genesis identity, and checksum. Rejected candidates move intact to `mempool-snapshot-rejected-*` and never block Chainstate. An unreadable or unquarantinable candidate blocks replacement. The gateway revalidates against recovered Chainstate while fee-estimator history stays independent. The index durability marker (`[0x00, b'V']`, format 9, covering key layout, row-value widths, and the tail log record layout) is the hard gate. A mismatch refuses open and recovery full-resets for rebuild. The affected capability reports unavailable or rebuilding and rebuilds from retained canonical data.

`rebuild-index` MUST publish compact filters only when the retained canonical archive starts at height zero. A pruned suffix has no trusted preceding filter header. The converter MUST omit filter rows, generation metadata, and the filter watermark for that suffix. It MAY publish transaction and script indexes for the retained coverage.
## Current persisted formats
KV chainstate uses the current durable layout with no translation layer; block files use `BRSB`; undo uses the current codec. RocksDB is the mandatory default storage engine; Fjall and redb are deleted from runtime and retained only in `tools/storage-convert` to read retired datadirs. In current epoch 6, authoritative coin state lives in the engine `coins` keyspace (`ColumnFamily::Coins`); no utxo v4 checkpoint coin image and no chainstate journal carry it. The resident `UtxoSet` is a rebuilt scan image primed from the engine coin store, never a durable authority. Restart resumes from the snapshot-base checkpoint published at activation; the retired `assumeutxo/` coin and header archive is gone and is never read. In retired epoch 5, authoritative coin state was the engine `coins` keyspace with the snapshot archive as the restart fallback and undo format version 1. In retired epoch 4, authoritative coin state was the engine `coins` keyspace with the snapshot archive as the restart fallback. In retired epoch 3, authoritative coin state was the resident `UtxoSet` (256-shard packed `UtxoRecord` per txid) backed durably by utxo v4 checkpoint artifacts and the chainstate journal. The offline converter verifies per-family digest equality between source copy and destination across persistent namespaces, except `UndoData` whose destination digest covers the recoded version 2 bytes. The suffix publication's coinstats are local to the converter run, cross-checked against the replay, and carry no external verification claim. Body-index rows must decode to 16-byte positions (lazy per-read validation; non-decoding rows are `IncompatibleData`). Magic, version, hash, checksum, ancestry, and semantic checks detect corruption in the current format only. They are not migration machinery.
## Approved checkpoint header compatibility
The writer MUST emit version 2 (`HEADER_VERSION = 2`); the reader MUST read versions 1 and 2 (`read_headers` gated by `is_readable_version` in `crates/execution/src/checkpoint/headers.rs`; `ACTIVE_ONLY_HEADER_VERSION = 1`). Version 1 holds active ancestry only; version 2 adds replayable side-branch headers. Both MUST pass manifest, digest, ancestry, commitment, and historical-header checks; side-header replay MUST NOT change the restored best tip. Unknown versions and corrupt artifacts MUST fail closed; the reader MUST NOT reset or convert an old artifact. No other legacy reader or migration is authorized.
## Schema changes
A change is breaking when a current binary cannot parse or safely interpret bytes written by another version (column-family names/discriminants, key/value layouts, block/undo records, every covered surface). Every breaking change increments the epoch, keeps one current writer and reader, adds the matching `tools/storage-convert` step; the node itself keeps one current reader and writer, keeps current-format integrity tests, and documents the resync-or-tool route into a separately named directory. The node must increment the datadir schema epoch when changing the bitcoin-rs-coinstats-v1 codec identifier or encoding. `Cold` is only the no-committed-head result (including an unpublished first write), never a compatibility mode.
| Epoch | Change | Status |
| --- | --- | --- |
| `0` | Initial baseline; unmarked non-empty datadirs are implicit epoch `0` and refused | retired |
| `1` | Head carries AssumeUTXO anchor, lifecycle, pending-validation and checkpoint references (frame version 3) | retired |
| `2` | Head binds checkpoint generation to publication-time manifest SHA256 (frame version 4) | retired |
| `3` | Engine set: RocksDB (default, always compiled), optional SurrealKV and libmdbx; Fjall and redb removed | retired |
| `4` | Coins in the engine `coins` keyspace; no chainstate journal; new checkpoints carry no utxo v4 coin image | retired |
| `5` | Snapshot activation publishes a checkpoint at the snapshot base; the `assumeutxo/` coin and header archive is removed and restart requires the checkpoint | retired |
| `6` | Undo records hold only spent coins (`UNDO_FORMAT_VERSION = 2`); created outputs are derived from block bytes | current |
## Removed settings and changed input syntax
Removed settings get no alias and changed grammars pin old spellings; no epoch moves and no datadir is touched. TOML unknown keys fail startup (the generated reader names accepted keys). CLI unknown flags fail parsing; `BITCOIN_RS_*` unknown variables are skipped. `bitcoin.conf` reads only the option-table keys (`dbcache`, `prune`, `rest`, `txindex`, `rpcuser`, `rpcpassword`, `rpccookiefile`, `scripthash-limit`) plus `listen`. Removed with no replacement: the `fast` validation mode (`--validation-mode fast`, `BITCOIN_RS_VALIDATION_MODE=fast`, TOML `validation_mode = "fast"`; the accepted values are `full` and `assume-valid`). Removed runtime storage backends: `--storage-backend fjall` and `--storage-backend redb` (`BITCOIN_RS_STORAGE_BACKEND=fjall|redb`, TOML `storage_backend = "fjall"|"redb"`); the accepted values are `rocksdb` (the default, always compiled), `surrealkv` (with the `surrealkv` feature), and `mdbx` (with the `mdbx` feature). Retired backends fail configuration validation with `unsupported storage backend <value>`, while the datadir refusal on incompatible datadir bytes names `bitcoin-rs-storage-convert`. Also removed: `--index-rollback-rebuild-cutover` / `BITCOIN_RS_INDEX_ROLLBACK_REBUILD_CUTOVER` / `index_rollback_rebuild_cutover` (owner: derived index runtime `DEFAULT_ROLLBACK_REBUILD_CUTOVER`, currently `100_000`). Also removed: flat per-topic `zmqpub*` keys with `...hwm` variants (ZMQ is TOML-only, grouped by endpoint; legacy flat keys are hard-rejected, never translated). `script_index` inputs (`--scriptindex`, `BITCOIN_RS_SCRIPTINDEX`, TOML `script_index`) accept `utxo`/`full` plus booleans (`true`/bare flag = `full`, `false` = disabled); any other value is a hard error; `--script-index` stays supported. Index capability semantics are owned by `docs/contracts/indexing.md` (`IDX-02`).
Also removed with no replacement in epoch 4: the `[chainstate_journal]` TOML table and the `BITCOIN_RS_CHAINSTATE_JOURNAL*` variables. A `[chainstate_journal]` table fails startup as an unknown key, like any other unknown TOML key.
