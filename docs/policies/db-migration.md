# Current datadir format policy
`bitcoin-rs` supports exactly one persistent datadir format for authoritative chainstate bytes. It does not migrate, translate, or silently recover incompatible state. A schema change increments `CURRENT_SCHEMA`; the operator moves to a separately named datadir by fresh replay, or by an optional epoch-specific offline tool when one is offered. Format breaks are permitted redesigns, not defects; operator data safety is the invariant.
## CURRENT_SCHEMA scope
`CURRENT_SCHEMA` covers only authoritative chainstate bytes: the durable head, the coin set, body and undo extents and references, and identity metadata. Owner-local state (fee estimator, peer discovery, mempool snapshots, index layouts) carries its own versions and never moves this marker. The current epoch is `2`. The marker is written and synced before any authoritative store opens (contents synced everywhere; the directory synced where the primitive exists). The node never deletes user data automatically. Network/backend datadir ownership and multi-process locking are configuration and lifecycle concerns outside this marker (tracked in issue #242).
| Datadir state | Startup action |
| --- | --- |
| Empty directory | Create and sync the current epoch, then initialize the current schema |
| Marker matches current epoch | Continue startup (no durable head yet starts cold) |
| Missing marker (implicit epoch `0`), malformed marker, other epoch, or head referencing missing/corrupt bytes | Refuse open with `incompatible_schema`; never open, convert, reset, or repair in place |
## Operator resync procedure
1. Stop the node on the old datadir. Keep the old datadir untouched; incompatible code never opens it.
2. Create a separately named datadir for the new schema epoch.
3. Replay the chain from the network (or an explicit archive/reindex input) with the new binary.
4. Verify identity before use: pinned stop identity (height, block hash), durable head hash, and recorded body/undo digests.
5. Body, undo, and metadata bytes and their directories are fsynced before the durable head commits.
6. Switch the manifest to the new store atomically; the switch touches the new store only.
The durable head is the only commit point: body/undo frames are appended and synced, then coins, head, and metadata commit in one atomic named-family batch. Crash residue is ignored: file length and valid frames never promote a head. An unresolved batch resolves to the prior or the wholly proposed root, never a mix. An optional offline tool (e.g. under `tools/`; none exists today and none is guaranteed) MUST read without mutating the source. It MUST produce a new datadir, verify identity and durability, and keep fresh replay as the fallback. Cutover is an explicit operator action on the tool's verification report. That report covers the provenance of every reused byte.
## Owner-local versions and degrade behavior
Authoritative startup never fails because of an owner-local version; rejected artifacts are preserved and quarantined, never silently deleted. Fee estimator state degrades to insufficient-data status (never a fabricated rate or confidence). Peer discovery is the canonical AddrMan v1 per [P2P compatibility section 7](p2p-compatibility.md#7-deviation-ledger). Schema version 1 remains until first release. Unmarked development snapshots are preserved byte-for-byte, never migrated; corrupt files disable replacement while startup continues. Mempool snapshots carry a mempool-owned version, genesis identity, and checksum. Rejected candidates move intact to `mempool-snapshot-rejected-*` and never block Chainstate. An unreadable or unquarantinable candidate blocks replacement. The gateway revalidates against recovered Chainstate while fee-estimator history stays independent. The index durability marker (`[0x00, b'V']`, row-format 6, covering key layout and row-value widths) is the hard gate. A mismatch refuses open and recovery full-resets for rebuild. The affected capability reports unavailable or rebuilding and rebuilds from retained canonical data.
## Current persisted formats
KV chainstate uses the current durable layout with no translation layer; block files use `BRSB`; undo uses the current codec. Storage stores CoinRecords rows as transaction records keyed by 256-bit txid with lossless canonical v5 payloads. Body-index rows must decode to 16-byte positions (lazy per-read validation; non-decoding rows are `IncompatibleData`). Magic, version, hash, checksum, ancestry, and semantic checks detect corruption in the current format only. They are not migration machinery.
## Approved checkpoint header compatibility
The writer MUST emit version 2 (`HEADER_VERSION = 2`); the reader MUST read versions 1 and 2 (`read_headers` gated by `is_readable_version` in `crates/chainstate/src/checkpoint/headers.rs`; `ACTIVE_ONLY_HEADER_VERSION = 1`). Version 1 holds active ancestry only; version 2 adds replayable side-branch headers. Both MUST pass manifest, digest, ancestry, commitment, and historical-header checks; side-header replay MUST NOT change the restored best tip. Unknown versions and corrupt artifacts MUST fail closed; the reader MUST NOT reset or convert an old artifact. No other legacy reader or migration is authorized.
## Schema changes
A change is breaking when a current binary cannot parse or safely interpret bytes written by another version (column-family names/discriminants, key/value layouts, block/undo records, every covered surface). Every breaking change increments the epoch, keeps one current writer and reader, adds no converter/legacy reader/adapter/fallback, keeps current-format integrity tests, and documents the resync-or-tool route into a separately named directory. The node must increment the datadir schema epoch when changing the bitcoin-rs-coinstats-v1 codec identifier or encoding. `Cold` is only the no-committed-head result (including an unpublished first write), never a compatibility mode.
| Epoch | Change | Status |
| --- | --- | --- |
| `0` | Initial baseline; unmarked non-empty datadirs are implicit epoch `0` and refused | retired |
| `1` | Head carries AssumeUTXO anchor, lifecycle, pending-validation and checkpoint references (frame version 3) | retired |
| `2` | Head binds checkpoint generation to publication-time manifest SHA256 (frame version 4) | current |
## Removed settings and changed input syntax
Removed settings get no alias and changed grammars pin old spellings; no epoch moves and no datadir is touched. TOML unknown keys fail startup (the generated reader names accepted keys; nested `chainstate_journal` carries `deny_unknown_fields`). CLI unknown flags fail parsing; `BITCOIN_RS_*` unknown variables are skipped. `bitcoin.conf` reads only the option-table keys (`dbcache`, `prune`, `rest`, `txindex`, `rpcuser`, `rpcpassword`, `rpccookiefile`) plus `listen`. Removed with no replacement: the `fast` validation mode (`--validation-mode fast`, `BITCOIN_RS_VALIDATION_MODE=fast`, TOML `validation_mode = "fast"`; the accepted values are `full` and `assume-valid`). Also removed: `--index-rollback-rebuild-cutover` / `BITCOIN_RS_INDEX_ROLLBACK_REBUILD_CUTOVER` / `index_rollback_rebuild_cutover` (owner: derived index runtime `DEFAULT_ROLLBACK_REBUILD_CUTOVER`, currently `100_000`; see `docs/benchmarks/index-rollback-rebuild-cutover.md`). Also removed: flat per-topic `zmqpub*` keys with `...hwm` variants (ZMQ is TOML-only, grouped by endpoint; legacy flat keys are hard-rejected, never translated). `script_index` inputs (`--scriptindex`, `BITCOIN_RS_SCRIPTINDEX`, TOML `script_index`) accept `utxo`/`full` plus booleans (`true`/bare flag = `full`, `false` = disabled); any other value is a hard error; `--script-index` stays supported. Index capability semantics are owned by `docs/contracts/indexing.md` (`IDX-02`).
