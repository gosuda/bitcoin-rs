# BIP adoption policy
This policy selects, prototypes, verifies, promotes, and retires BIP-based capabilities. Per-surface status lives in [ecosystem-compat.toml](../api/ecosystem-compat.toml); the wire matrix in [p2p-compatibility.md](p2p-compatibility.md); the RPC surface in `REGISTRY` (`crates/rpc/src/registry.rs`).
## 1. Classification
| Class | Rule |
| :--- | :--- |
| Active consensus rules | Mandatory exact behavior; Core, `libbitcoinkernel`, vectors, historical-chain replay, and differential tests are reference evidence. No experimental consensus deviations on mainnet. |
| Proposed or unactivated consensus changes | Research, regtest, or explicitly isolated test-network experiments only. No mainnet enforcement or activation claims before network activation. |
| P2P, transport, relay, and policy BIPs | Prototype when peers, negotiation, fallback, and network safety are verifiable. A Core merge is useful evidence, not a gate. |
| Wallet discovery, indexing, and application-layer BIPs | Optional node services with a credible consumer or clear research value. Wallet secrets and per-user state stay outside the node by default. |
| Wallet-only formats and out-of-scope BIPs | Not node features by default; document the node-facing use instead of implementing every BIP. |
## 2. Adoption decision
Record the adoption decision in the existing issue or PR. Keep implementation work in each issue. External prototypes follow [CONTRIBUTING](../../CONTRIBUTING.md#proposing-and-implementing-bips). Do not create a new tracking database or mandatory prototype CI gate. Record the exact BIP version or pinned draft commit. Separate stable and experimental APIs. Record the consumer, use case, and hypothesis. A research prototype is valid before demand exists. Record consensus and sync impact. Record P2P interoperability and negotiation. Identify the owning crate and state. Reuse block, undo, and UTXO state before adding new rows, workers, or APIs. Record consequences for CPU, memory, disk, IO, backfill, pruning, AssumeUTXO, restart, reorg, and DoS. Keep work bounded and state unavailable conditions explicitly. Document validation evidence. This evidence includes reference vectors, independent implementations, unmodified external consumers, regtest runs, and whole-node regressions. Promotion to enabled or shipped requires a higher bar. No scorecard or registry is required at any stage.
## 3. Implementation and rollout rules
Consensus invariance is non-negotiable: an optional BIP MUST NOT alter consensus validity, chainstate authority, or block acceptance. Extensions reuse `BlockBodySource`, `BlockUndoSource`, derived-index lifecycle, RPC/P2P adapters, and mutation owners: no parallel UTXO truth, duplicate schedulers, or plugin frameworks. Experimental BIPs stay independently implementable, testable, and disableable (default off until resource/compatibility effects are proven; negligible disabled overhead). Never advertise (service bit or API support) before end-to-end interop exists; use existing status inventories (`docs/contracts/ecosystem-compatibility.md`, `crates/rpc/src/manifest.rs`). Small and reversible first (vectors/codec, bounded reads, persistence only if justified; removable when measured costs exceed value). No starvation of IBD, mempool, or services: budgets, cancellation/backpressure, and failure isolation (`CONSTRAINTS.md`). Core is a reference, not a permission: compare against pinned Core; no Core-merge gate for non-consensus features.
## 4. Lifecycle
| Stage | Entry evidence | Exit evidence |
| :--- | :--- | :--- |
| Research | Feasible design over an existing owner; pinned BIP draft; stopping failure modes | Reference vectors pass; bounded resource story; consumer or research value holds |
| Experimental | Default-off implementation over existing owners; typed failures; bounded work | In-tree vector/regression suites pass; end-to-end behavior in a test context |
| Shipped | End-to-end interop with an unmodified external consumer; measured cost; docs and tables updated in the same change-set | Promoted rows in `ecosystem-compat.toml` and owning status inventories |
Any stage can end as `Deferred` or `Rejected` (incompatibility, pruning limits, or weak adoption justify deferral without a defect claim). P2P "shipped" additionally requires the live Core evidence lane or an equivalent unmodified external consumer per `ECO-08`, scoped by `ECO-09`; an in-tree test never upgrades external verification.
## 5. Coverage map maintenance
The matrix lives in [bip-support.md](../bip-support.md) (symbols `Implemented`, `Partial`, `Experimental`, `Planned`, `Unsupported`; `Implemented` means in the merged tree, not `Shipped`); external runs record only in [ecosystem-compat.toml](../api/ecosystem-compat.toml), updated in the same change-set as the code. Verify every status against the merged default branch, never a PR head or open issue. Support, promotion, and verification are distinct claims: a checkmark never establishes `Shipped` or `Externally Verified`. Open PRs and active issues are `Planned`; deferral-only notes and rejected issues stay `Unsupported`; `Experimental` means merged but default-off or draft-pinned. Never publish an "X% of all BIPs" metric (no single denominator: many BIPs are wallet-only, informational, or inapplicable). No runtime registry, state machine, or CI gate exists just to render the matrix.
## 6. Applied decisions
#1502 BIP157/158 compact filters (application-layer; `Shipped`): optional `blockfilterindex` exists in the merged tree. It includes recorded unmodified Kyoto regtest verification (see `ecosystem-compat.toml`). It provides no stale-block filters or scanblocks. We make no production mainnet IBD performance claim. Esplora and ScriptIndex remain the default self-hosting path.
#1491 BIP352 Silent Payments (wallet discovery; `Experimental`): a keyless stateless scan codec sits behind the `silent-payments` Cargo feature. Wallet scan keys and per-user history never enter the node. A thin public-tweak index follows in #1491. The upstream index-server specification is a work in progress. Pin the commit under test. Never present provisional endpoints as stable. Hosted remote-scanner models stay out of scope by default. They hold wallet secrets, which creates a worse privacy boundary.
#1503 BIP324 v2 transport (P2P transport; `Shipped`, on by default as Core's `-v2transport`): bidirectional interop holds with unmodified Core 31.1. See `ecosystem-compat.toml` and CORE-06. Recorded 250-block regtest cost (PR #1612): v2 received 119,945 and sent 11,166 bytes vs v1 119,120/9,626. BIP324 allows up to 4,095 handshake-garbage bytes per direction per connection. Single-run timings were 3.5-4 µs per packet and 510-550 MB/s for 1-4 MB payloads (2.1 GHz Xeon core, release). These ad hoc timings are not reproducible from the tree. We claim no active-MITM or eclipsing-peer protection.
#1501 BIP330 Erlay (P2P relay; `Deferred`): this note records no BIP330 support. We read the status on 2026-10-31. Tracking issue #30249 leaves reconciliation request, response, and extension steps unchecked. The full implementation is PR #35591, titled `[DO NOT MERGE]`. It has remained open since 2026-06-23 with 38 commits, 30 files, and +4426 -402 lines. Its author states that it uses `sendtxrcncl` for an unplanned purpose. The design remains undecided. RFC issue #34542 proposes a separate reconciliation connection class, but reviewers prefer simpler changes. PR #30116 fills reconciliation sets and has stayed open since May 2024. Five owners would change in this repository. Connection admission (`crates/p2p/src/connection.rs`, `crates/p2p/src/listener.rs`) gains an inbound reconciliation connection limit. Capability negotiation (`crates/p2p/src/handshake.rs`, `crates/p2p/src/compat.rs`, `crates/p2p/src/peer_info.rs`) gains a typed `sendtxrcncl` exchange. Relay scheduling (`crates/p2p/src/tx_policy.rs`, `crates/p2p/src/tx_policy/relay.rs`, `crates/p2p/src/inv.rs`) adds a reconciliation timer. Mempool authority (`crates/mempool/src/gateway.rs` and the owning node state) feeds the reconciliation set. Resource limits (`crates/p2p/src/tx_policy/ingress.rs`, `crates/node/src/state/open.rs`, `crates/p2p/src/wire.rs`, and `crates/p2p/src/transport.rs`) gain per-peer set and sketch bounds. The sketch code adds a minisketch dependency. Today `sendtxrcncl` stays untyped in `CORE_UNTYPED_COMMANDS` (`crates/p2p/src/compat.rs`). A ready peer ignores it like any unknown command. The test `unknown_commands_are_ignored_once_ready_like_core` (`crates/p2p/tests/core_compat.rs`) guards this behavior. The wire stays Core-compatible. Reopen when a non-draft Core PR merges reconciliation request and response paths. BIP330 must pin a stable message set, and a local regtest lane must show a measured benefit. Parity is not a trigger. Closing as not planned stays available if Core abandons the project.
Evidence for #1501: Core state comes from [#30249](https://github.com/bitcoin/bitcoin/issues/30249), [#34542](https://github.com/bitcoin/bitcoin/issues/34542), [#35591](https://github.com/bitcoin/bitcoin/pull/35591), and [#30116](https://github.com/bitcoin/bitcoin/pull/30116). We read these sources on 2026-10-31 (tracking checkboxes, PR title, commit and diff counts, and discussion text). This repository proves untyped-command behavior. `cargo nextest run --locked -p bitcoin-rs-p2p -E 'test(core_compat)'` ran 29 tests on 2026-10-31. It completed with 29 passed and 1,290 skipped. Passing tests include `unknown_commands_are_ignored_once_ready_like_core` and `listed_commands_type_and_core_untyped_commands_stay_unknown`.

#1625 dormant P2PK outputs (`Research`, phase 1 only): `tools/p2pk-scan` lists every unspent pay-to-pubkey output with outpoint, height, and value. It replays a raw block file through the UTXO read path. The tool links the UTXO crate and keeps its own in-memory set. It never opens a node data directory, so default node behavior does not change. Its README records the example dataset, verification commands, and false-positive and false-negative limits. Phase 1 settled enumeration only. The shape rule is reproducible because the workspace owns it in `bitcoin_rs_script::is_p2pk`. Operators can cross-check real datasets with Core `scantxoutset` and `gettxoutsetinfo`. Phases 2 and 3 need a selector to identify qualifying dormant outputs. Five candidates exist.

| Candidate | Reproducible by a second party | Defensible | Node effect |
| :--- | :--- | :--- | :--- |
| Selection rules: shape plus an age and value threshold | Yes, when the rule set is published with the dataset | No: the thresholds are a policy guess, and no published rule set exists | Policy only |
| Fixed manifest: a committed outpoint list | Yes to check, no to derive | No: no party can derive the list independently, and it drifts with the chain | Policy only |
| Freeze: refuse to relay or mine spends from selected outputs | No: the list stays node-local | No: it adds a censorship surface with no independent evidence | Relay and mining policy |
| Throttle: rate-limit spends of selected outputs | No: same local-list problem | No: it changes relay behavior without a measurable harm | Relay policy |
| No action: keep the read-only scan | Yes | Yes | None |

No candidate met both bars, so phases 2 and 3 do not start. Reopen when an operator or third party publishes a selector. That selector must provide criteria and a dataset that a second party can reproduce with `tools/p2pk-scan`. That party must also be able to cross-check the dataset with Core. A manifest without a derivation rule does not meet that bar.
Evidence for #1625: `cargo test --locked -p bitcoin-rs-p2pk-scan` passes six tests on 2026-10-31. These tests include the fixture report, reordered-file refusal, malformed-line refusals, and the shape rule. A mutation probe disables the header-linkage comparison. The reordered-file test then fails with an incorrect UTXO set (109 outputs, 2 P2PK rows instead of 110 and 3). [tools/p2pk-scan/README.md](../../tools/p2pk-scan/README.md) holds the committed 103-block regtest dataset, its exact report, and Core cross-check commands.
#1514 snapshot bootstrap artifacts (application-layer/indexing; `Research`): Core v2 `dumptxoutset` export is the first reversible step. Index sidecars never pose as Core format. #1488 Lightning backends (external interop evidence; `Research`): each backend represents one row of external evidence, not a node feature.
