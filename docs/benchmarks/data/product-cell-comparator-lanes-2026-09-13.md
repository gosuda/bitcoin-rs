## Why the live product-cell arms did not run
The #34 offline lane needs bitcoin-rs to apply a Core-framed archive at `assume_valid_height 0` to the manifest stop height, then persist bodies, undo, and the production checkpoint, and exit. The #41 lane needs a bitcoin-rs node whose committed UTXO set at height 150,000 answers `gettxoutsetinfo` with the CORP-05 oracle values. The #35 P2P lane needs a live loopback IBD between real Core 31.1 and bitcoin-rs nodes. None of these can start from this tree: `bin/bitcoin-rs/src/cli.rs` exposes no corpus, manifest, archive, blocks-dir, or stop-at-height flag (only `run` and `measure_storage`); `crates/node/src/import.rs` is an explicit skeleton whose `import_block` is not wired to any archive source or CLI path (both paths present at this record's date; `import.rs` deleted 2026-09-17 in `c64f82be4`, `cli.rs` consolidated 2026-10-03 in `f9c06fb4c`); `gettxoutsetinfo` (in `crates/rpc/src/handlers/chain.rs`) answers the current in-memory UTXO view but refuses specific-height queries, and no shipped offline path places the node at the frozen tip with certified state; the P2P lane's product form is not shipped (`tools/benchmark-campaign/p2p_loopback.py` is a scripted-peer fixture harness, the historic `mainnet_prefix_replay` tool was retired), while a live loopback IBD has no stop-at-height and the comparator requires RPC-ready within `ARM_READY_TIMEOUT_NS = 10 s` (`tools/benchmark-campaign/muhash_rpc.py`) on pre-constructed state the missing ingest path cannot supply.
Consequently no Core-vs-bitcoin-rs campaign ran: the candidate arm cannot be placed at the frozen tip, and running the Core side alone would produce the one-arm, no-counterpart evidence the contract refuses (`HPA-08`). This is a capability/harness blocker, not a custody blocker (#34 and #35), and a state-construction budget blocker, not an RPC absence (#41: the RPC is implemented; the state is constructible only via a long IBD with no stop-at-height or shipped harness).
