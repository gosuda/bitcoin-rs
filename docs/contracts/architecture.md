# Architecture contract

The normative contract for workspace crate layering, one-way dependency direction, storage engine confinement, and composition boundaries.

These boundaries are internal architecture, not a compatibility promise. A demonstrated better internal design may redraw them. The `ARCH-06` change process governs layer assignments and workspace dependency boundaries.

Owners:
- `Cargo.toml`, `crates/*/Cargo.toml`, `bin/bitcoin-rs/Cargo.toml`; workspace dependency gate in `bin/bitcoin-rs/tests/gates/g17_dependency_direction.rs`
- `KvStore`, `KvSnapshot`, `PrefixScanLimit`, `PrefixScan` in `crates/storage/src/trait_.rs` (bounded prefix scans, `ARCH-02`)

## Layer model

| Layer | Crates | Responsibility |
| --- | --- | --- |
| 4: Compose | `node`, `bitcoin-rs`, `e2e`, `storage-footprint`, `snapshot`, `storage-convert`, `p2pk-scan`, `contract-index` | Runtime assembly, lifecycle, and offline tooling |
| 3: Surface | `serving` | External protocol boundaries |
| 2: Services | `execution`, `wire`, `mempool`, `projection` | Domain state and services |
| 1: Storage | `storage` | Storage contracts and engine drivers |
| 0: Core | `consensus` | Protocol types and validation, without storage or I/O |

Crate names use the `bitcoin-rs-` prefix except for the `bitcoin-rs` binary and `contract-index`.

## Clauses

### `ARCH-01`: Five-layer one-way dependency direction

- Every workspace crate belongs to an approved layer (0 to 4). Production and build dependencies may point only to the same or a strictly lower layer; below Layer 4, the only permitted same-layer edge is `projection` -> `execution`. Upward or otherwise forbidden edges fail the `g17_dependency_direction` gate. The resolved production and build dependency graph is a directed acyclic graph. Any cycle, even within one layer, fails the gate.
- The [layer model](#layer-model) assigns every crate. Layer 0 crates have zero dependencies on storage, network, or filesystem I/O.
- In Layer 2, `execution` is the authoritative applied-chain owner and owns the `chain` module. Its internal workspace dependencies are `consensus` and `storage`. It MUST NOT depend on mempool, wire, projection, serving, node, or the binary. The former standalone primitives and script crates are modules in `consensus`; UTXO storage and codecs live in `storage`. Mining orchestration lives in `node`, not a separate Layer 2 crate.
- `wire` and `mempool` are Layer 2 crates, but neither depends on the other. `wire` depends on `consensus` and `storage`; `mempool` depends on `consensus`. `mempool` MUST NOT depend on `wire`, `serving`, `node`, or the binary. Admission retains peer attribution as data, never connection ownership. The gate checks this boundary. Node owns P2P sync and the composition between wire, execution, mempool, and projection. `projection` -> `execution` is the sole permitted same-layer domain dependency.
- In Layer 4, the footprint package is an offline Linux filesystem utility with no node, runtime-workspace, or storage-engine dependencies. `bitcoin-rs-snapshot` is an offline Core-file inspector and verifier using `consensus` and `storage` for shared protocol types and UTXO codecs. It composes no node, P2P, RPC, mempool, or mining runtime. `bitcoin-rs-e2e` drives the composed daemon and the pinned reference node over public surfaces; it declares an internal dependency on `bitcoin-rs-serving`. Production workspace crates MUST NOT depend on the e2e harness; serving's dev-dependency on it is outside the production/build dependency graph checked by g17.
- Explicit non-goal: layer numbers do not justify speculative new crates or thin wrapper layers. A boundary exists only to isolate external dependencies, enforce safety or consensus boundaries, or separate independent runtime lifecycles.

### `ARCH-02`: Exclusive storage engine dependency ownership

- `bitcoin-rs-storage` is the only crate permitted to depend on storage engine crates (`rust-rocksdb`, `surrealkv`, `signet-libmdbx`, and `tokio` for the SurrealKV bridge only). No other crate may name an engine dependency in `[dependencies]`, `[build-dependencies]`, or `[dev-dependencies]`. Only `bitcoin-rs-storage-convert` can name `fjall` and `redb`, to read retired datadirs. Higher layers reach persistent state only through the `KvStore` facade and storage abstractions. Storage owns checkpoint formats, recovery evidence markers, filesystem operations, durability primitives, and the optional bounded `HistoryAccess` consumer role. No chainstate journal format exists.
- Bounded prefix scans: `scan_prefix_bounded` and `scan_prefix_from_bounded` on `KvStore` and `KvSnapshot` return a bounded part of one column family's rows under a prefix. `PrefixScanLimit { max_rows, max_bytes }` bounds one scan. `max_rows` caps returned rows, and zero returns none. `max_bytes` caps the running total of returned key-plus-value bytes. The first row is exempt. The scan returns the first row even when it alone exceeds `max_bytes`, and counts it. Each later row is returned only when the total including it stays at or below `max_bytes`. For example, with `max_bytes` 10 and rows of 6 and 5 bytes, the first is returned and the second refused. A row whose byte count overflows `usize` is refused. `PrefixScan { rows, complete }` holds rows in key order. `complete` is true only when the scan reached the end of the prefix with no row refused. An implementation MUST NOT report `complete = true` after refusing a row. An exact-fit limit is complete. A zero-row limit is complete only when no row matches. A store that cannot serve a scan MUST return an error, never an empty or falsely complete scan.
- Seek point: `scan_prefix_from_bounded(cf, prefix, start)` takes an inclusive full-key `start`. Rows begin at the first key at or above the greater of `start` and `prefix` in byte order. Rows end where keys stop beginning with `prefix`. A `start` before the prefix (including the empty slice) begins at the first row. A `start` past every key of the prefix yields an empty, complete scan. This includes a `start` that sorts after the prefix without beginning with it. Resuming after returned row `k` passes `k` followed by one zero byte, the least key above `k`.
- Required versus defaulted methods: `iter_prefix` and `scan_prefix_from_bounded` are required on both traits with no default body. Every `KvStore` and `KvSnapshot` MUST provide both methods. `scan_prefix_bounded` has a default body on both traits that collects from `iter_prefix` under the same limit. RocksDbStore and its snapshots use the default body.
- Backends (RocksDB `IteratorMode::From`) seek natively to the greater of `start` and `prefix`. They never collect and then discard a prefix head. A scan stops at the first row the limit refuses. It reads at most one row past the limit and drops it.
- Specialized fixed-width txindex stores from retired engines (such as redb) are removed; RocksDB serves all column families through the unified `KvStore` facade.
- Snapshot reads see the view captured by `KvStore::snapshot`. Rows committed after the snapshot are invisible. Pages read through one snapshot read one view. The limit bounds returned rows only. It allows at most `max_rows` rows. It allows at most the greater of `max_bytes` and the first row's key-plus-value size (an oversized first row is returned whole). The limit does not bound engine-internal reads or caches. It does not bound a transient copy of the row it refuses.
- Consumers: `bitcoin-rs-projection` calls `KvSnapshot::scan_prefix_bounded` for txid, scripthash, spending-outpoint, and live-output lookups (`StoreTxIndexSnapshot::scan`, `live_rows`, `crates/projection/src/index/snapshot.rs`). `QueryBudget::next_scan_limit` (`crates/projection/src/runtime/query.rs`) derives each limit from the query's remaining row and byte budget. `accept_scan` and `accept_live_scan` turn `complete = false` into `TxUnavailableCause::PrefixScanTruncated` and `LivePrefixScanTruncated`, never a partial answer. Capability reset (`crates/projection/src/index/state.rs`) calls `KvStore::scan_prefix_bounded` under `RESET_SCAN_LIMIT` one page at a time. No production code calls `scan_prefix_from_bounded`; storage tests do.

### `ARCH-03`: Storage backend feature forwarding confinement

- Runtime backend features (`fjall`, `redb`, `rocksdb`) are removed from `crates/storage`, `crates/node`, and `bin/bitcoin-rs`. RocksDB is mandatory and non-optional in `bitcoin-rs-storage`; the default binary and node runtime compile RocksDB unconditionally.
- Layer 0 (Core) and Layer 3 (Surface / Serving) crates MUST never define or forward storage backend features. The Layer 2 crates `bitcoin-rs-wire` and `bitcoin-rs-mempool`, and the Layer 3 crate `bitcoin-rs-serving`, MUST NOT define or forward backend feature names. An empty `rocksdb = []` marker counts as defining one and is forbidden. For the optional `surrealkv` and `mdbx` features, g17 permits definitions and forwarding only in `bitcoin-rs-storage`, `bitcoin-rs-execution`, `bitcoin-rs-projection`, `bitcoin-rs-node`, `bitcoin-rs`, and `bitcoin-rs-storage-convert`.
- RocksDB is the mandatory default engine. `fjall` and `redb` are removed from runtime; retired datadirs are migrated offline using `tools/storage-convert`.
- `crates/node/src/storage_backend.rs` is the sole owner of concrete runtime backend construction in the node. Chainstate and txindex each cross that boundary once to open `RocksDbStore::open_with_cache`. They then compose backend-neutral capabilities for undo, pruning, the coin store and its cache, indexing, and footprint inspection. The consumer visitor is only a composition seam. `KvStore` owns reads, writes, batches, and durability.

### `ARCH-04`: Serving surface independence from storage

- `bitcoin-rs-serving` MAY depend directly on `bitcoin-rs-storage` for backend-neutral capabilities and shared storage-owned types. Direct reuse keeps these interfaces with their storage owner instead of duplicating them in forwarding wrappers. It MUST have zero dependencies on storage engine crates (`rust-rocksdb`, `surrealkv`, `signet-libmdbx`). It consumes node capabilities (chain, mempool, index, network, mining, coins) exclusively through the capability groups that `Context` stores (`ChainHandles`, `MempoolHandles`, `IndexHandles`, `NetworkHandles`, `MiningHandles`, `PoolHandles`). These include storage-owned readers, statistics, block-body sources, and undo sources. It MUST NOT bypass the supplied capabilities for database access or chain transitions. `Context::from_handles(ContextHandles)` is the single production composition point. One `ContextHandles` value carries every capability. Production wiring attaches nothing to a built `Context`. `bitcoin-rs-serving` MUST NOT define or forward storage backend features.

### `ARCH-05`: Node composition and orchestration boundary

- `bitcoin-rs-node` (Layer 4) is the assembly and lifecycle orchestration layer. It wires storage backends, consensus validators, mempool gateway, P2P listeners, index reconciliation workers, and RPC services into an executable node runtime. Domain mechanics live in domain crates. Consensus rules live in consensus/script. `MempoolGateway` owns mempool admission preparation, retry, orphan bodies and indexes, ready-orphan work, and recent rejects. Node only loads at open and saves at shutdown the fee-estimator history file format and atomic datadir persistence in `fee_history` / `fee-estimator-history.dat`. Connection lifecycle lives in p2p (transaction inventory implementation, missing-parent requests, source-connection checks, bounded relay queue/worker/saturation policy). Template assembly and the mining control contract live in mining. Index schemas live in their owning crates. Node supplies the chain view. Node connects committed admission results to relay and mining. Node owns channel wiring and worker startup and shutdown. Node keeps no second admission-state store or transaction policy implementation. Admission sequencing follows [MPL-04](mempool-mutations.md). Wire behavior and deviations follow [P2P-01](p2p-wire.md).
- `bitcoin-rs-serving::mining` owns `Candidate`, `BlockTemplate`, `MiningInfo`, `MiningControl`, and the candidate lifecycle. That lifecycle includes the `(applied_tip_hash, mempool_sequence)` generation key, bounded template cache with single-flight assembly, long-poll publication, and BIP22/BIP23 projection (`MiningService`, fed by node-owned capability sources). Mining also owns `MiningGenerationSignal` (authoritative-mutation wake seam, `generation_signal`), `getnetworkhashps` estimation (`network_hashps`), and the BIP22/`submitheader` reject vocabulary (`bip22`). Serving maps those types onto BIP22/BIP23 JSON. Serving caches no templates and runs no long-poll.
- `bitcoin-rs-node` owns runtime startup and shutdown sequencing, configuration resolution and validation (`UserConfig` layers → `NodeConfig`), and the mining control facade. The mining control facade is `MiningCoordinator`. It composes the mining lifecycle service with chainstate read and transition capabilities, submits solved blocks, and requests header admission from chainstate. `bitcoin-rs-node` owns watch-only coinbase payout configuration (`MiningConfig::payout_script`, decoded once after every layer against the resolved network). It also owns process-level cache budgeting (`dbcache` across chainstate and txindex namespaces). The node option table (`crates/node/src/options.rs`) declares every operator option once with its value grammar and its spelling on each process-input surface. The `bitcoin-rs` binary expands that table into argv, environment, TOML, and `bitcoin.conf` readers. The binary holds no option name or grammar of its own beyond the two configuration-file selectors and the storage-measurement flags.
- `bitcoin-rs-execution` (`ARCH-07`) owns applied-tip mutation, recovery, checkpoint publication, mandatory retention consumption, and branch switching. A public field bag of subsystem handles does not own them. Retained-history *authority* (registry, executed frontier, prune reserve/commit) is owned by `bitcoin-rs-storage::pruning`. Node composes that one authority into chainstate, the prune service, and bounded index history.
- `bitcoin-rs-serving::zmq` owns topics, framing, HWM validation, socket transport, mempool sequence projection, and live notifier enumeration. `bitcoin-rs-node` constructs and wires the publisher. It owns when committed chain effects are emitted. The same live publisher sources `getzmqnotifications`, and node keeps no parallel notifier model. The `g17_dependency_direction` gate pins the external `zmq` dependency to the surface crate. It permits node only to forward `bitcoin-rs-serving/zmq`. `ARCH-07` owns transition reservation and post-commit follower dispatch.
- `resolve` folds every layer through `UserConfig::overlay` in precedence order, lowest first. A set field replaces the earlier value, while an unset field leaves it. Nested override structs merge the same way (including `MiningOverrides`). `overlay` also applies the RPC credential style rule inside the layer being folded. A later password clears an inherited cookie path, and a later cookie path clears inherited user and password. After the fold, the winning `network` value fills the profile-owned fields once via `NetworkProfile::for_selection`. Finally, `rpc_auth` chooses the final credential style from the winning values.

### `ARCH-06`: Hierarchy change and exception process

- Any change to workspace crate layer assignments, new workspace crates, or cross-crate dependencies REQUIRES three steps. (1) Update the `approved_layer` table or engine crate assertions in `bin/bitcoin-rs/tests/support/dependency_graph.rs`, used by `bin/bitcoin-rs/tests/gates/g17_dependency_direction.rs`. (2) Update this contract (`docs/contracts/architecture.md`) with the rationale and invariant justification. (3) Pass the `g17_dependency_direction` gate test. Automated gate enforcement in CI rejects speculative or circular dependency edges violating the one-way flow.
- Approved edge: `bitcoin-rs-storage-convert` (Layer 4) depends on `bitcoin-rs-execution` (Layer 2) so the offline 3 -> 4 conversion can publish an epoch-4 checkpoint at a durable head above the source checkpoint through `recovery::publish_converted_checkpoint`, which reuses execution's checkpoint publisher. Invariant: only the converter takes this edge; no node-side crate depends on `bitcoin-rs-storage-convert`; the published header tree is the verified source checkpoint tree extended with replayed, validated headers. The layer model records the converter's approved Layer 4 assignment, matching `approved_layer` in `bin/bitcoin-rs/tests/support/dependency_graph.rs`; this edge points downward and requires no same-layer exception.

### `ARCH-07`: Chainstate owns authoritative applied-chain mutation

- `bitcoin_rs_execution::Chainstate` is the in-process owner of applied-tip mutation, recovery, branch switching, checkpoint payload assembly/publication, and mandatory retention consumption. `NodeState`, `BlockSync`, mining, and RPC chain-control hold or clone that service. They do not assemble a transition from independent locks. Retained-history *authority* is not chainstate's. `bitcoin-rs-storage::pruning` owns the `RetentionRegistry`, the executed frontier, and prune reserve/commit. Node composition seeds that one registry and distributes it. Chainstate receives [`bitcoin_rs_storage::MandatoryRetention`] for transition pins. It receives the existing bounded `HistoryAccess` role for optional block-input queries. Both originate from that same registry. Neither can prune, commit, or shut down retention. Chainstate is not a broker for the registry.
- `BlockUndoSource` is implemented directly by `Chainstate`. RPC holds only that read trait. A query captures the caller's applied hash, full durable receipt, and storage-owned history lease under the transition domain. Bounded body and undo reads and projection run outside tree, write, and transition locks. Exact receipt, applied-hash, and lease revalidation follow. Historical snapshot prefixes need durably archived validation progress. Retained bytes alone never establish validation. The current undo extent may certify a disconnected branch until a later receipt replaces it.
- `Chainstate::begin_transition` and `TransitionLock::into_transition` are the only constructors of a `ChainTransition`. Reorg planning that must abort without mutating takes `lock_transition` first. It promotes that lock with `into_transition` only after the authoritative plan matches the preloaded plan.
- Snapshot reads (`Chainstate::snapshot`) copy the independently published header tip and a coherent applied-tip and chain-tx-count pair. They take no transition lock and cannot mutate chainstate. `ChainEventPublisher` cells remain a separate coherent applied-tip snapshot for index consumers (`EVT-01`).
- Long-lived RPC, P2P, index, and mining consumers receive `TipReader`, `BlockTreeReader`, and `StableRead` capabilities. Readers expose snapshot load and tree read guards. Every `&self` tree accessor is a pure read. The tip publication cell is shareable only through `&mut BlockTree`. `StableRead` excludes authoritative transitions while a coherent read runs. Its only production verbs are `lock` and bounded `try_lock_for` (zero timeout = immediate attempt). It hands back an opaque guard. It exposes no route to its matching `TransitionAuthority` (the role chainstate and destructive pruning hold across a mutation). `NodeState::open` mints one `TransitionDomain` per node and distributes matching roles to production consumers. `Chainstate` publishes no fence. `Chainstate::read_fence` does not exist and the g17 facade gate denies it. This is a production-wiring guarantee, not type-level provenance. `TransitionDomain::new`, `Default`, and `stable_read` are public. `ChainHandles::default` in the public `Context::new` fixture mints a private domain. Therefore, passing such a role to a live node reader does not exclude that node's transitions. Header admission uses `Chainstate::admit_headers`. Normal genesis connect publishes through the tree's shared tip cell with no separate fallback. Short-lived `ChainAdmissionView` values borrow readers. The P2P transaction ingress worker acquires its owned readers once at startup.
- `Chainstate::validate_block` dry-runs the apply path's pre-write consensus gates under `lock_transition`. It takes no mempool generation and persists nothing. BIP22 proposal omits proof-of-work. Every other pre-write gate is the same function commit runs. Owner: `crates/execution/src/lib.rs`. Authoritative apply lives in `crates/execution`. It holds and imports no mempool, RPC, ZMQ, index, mining, P2P, or node types. Apply publishes the tip and returns a `ConnectOutcome` or `DisconnectOutcome`. Capture flags are set at construction so apply can produce `rawtx` and canonical block bytes without holding the consumers.
- Node owns cross-domain sequencing around a chain transition. It reserves the mempool generation, dispatches `ChainFollowers`, and publishes the stable mempool generation before dropping the chain transition. Follower-free convenience methods are compiled for tests or the `test-seam` capability only. In-workspace production dependencies and feature forwarding MUST NOT enable that capability. Production uses explicit transitions plus follower settlement. Downstream users may explicitly opt into `test-seam`. RPC `BlockLog`, hash/raw ZMQ, TxIndex wake, sequence `C`/`D`, mining generation, admission, block-confirmation eviction, and reorg reconsideration run from node-owned dispatch. Consumer failure cannot invalidate chainstate. Issue #77 owns the durable event journal. This is dependency direction, not a second event contract. Cross-store ordering MUST NOT be pushed into `storage`.
- Reorg planning, body retention/loading, disconnect/connect execution, invalidation, and checkpoint-debt settlement live in chainstate. Node supplies a `ReorgObserver` for mempool/follower effects. Node holds the mempool generation fence around the operation. Reorg body memory is bounded by the chainstate streaming window. Chainstate retains no whole departed branch.
- Runtime capability ownership stays with the mutating subsystem. `P2pService` owns peer sessions, bans, the network-active latch, and header, block, and outbound channels. `ChainFollowers` owns the RPC block log, ZMQ publisher, and mining-generation signal. `Chainstate` owns the IBD latch. `NodeState` composes those services and returns their handles without retaining parallel fields. The inbound transaction channel is node-owned because node orchestration drains it into `MempoolGateway`. Confirmed transaction bodies are queried through the derived index and durable block storage, never through a second node or RPC transaction map. RPC network answers and control operations read and mutate network state through `P2pService` directly. This includes the peer table, traffic counters, ban list, added-node list, and network-active latch. It also includes bans, added nodes, network-active toggling, and disconnections via service control methods. RPC receives no raw handles for bans, added nodes, the latch, or the outbound dial channel. No parallel RPC-local network-state projection or duplicate mutation authority exists.
- `MempoolGateway` owns the process mempool handle. `NodeState::mempool` is a borrowed read and composition capability, not a parallel retained `Arc`. Gateway interning is the public one-gateway-per-pool-ledger enforcement boundary for test seams and downstream composition. The ledger is `bitcoin_rs_mempool::Mempool` (defined in `crates/mempool/src/pool.rs`, re-exported at the crate root since `mod pool` is private). It includes the entry arena plus derived txid/wtxid/funding/spending/priority indexes behind the gateway's `Arc<RwLock<Mempool>>` handle. Production constructs that same owner once. `NodeState` retains `PruneService` as a node/storage mutation capability because it is created only after chainstate supplies prune authority. It is handed to the later RPC lifecycle. It contains no duplicate block or transaction projection.

### `ARCH-07a`: Chainstate mutates `utxo` through one narrow contract

`bitcoin-rs-storage` is not a second mutation authority. It holds the engine coin store (`CoinStore` over `ColumnFamily::Coins`), the resident `CoinCache` read cache, and the recovery formats. Chainstate drives it through one coherent apply, commit, and disconnect contract (`crates/storage/src/utxo/contract.rs`, `crates/storage/src/coins.rs`, `crates/storage/src/commit.rs`).

- **Apply**: `build_block_changes` turns one validated block into its `BlockChanges`, its `UndoBatch`, and the `BlockValueTotals` needed for the coinbase check. Resolved prevouts enter through `SpentOutputLookup`. At BIP30 exception heights the block's coinbase outputs replace live coins, and the undo records each replaced outpoint as a remove, as Bitcoin Core does. **Commit**: `WindowDelta` folds one final coin image per touched txid, and `CommitAuthority::commit_prefix` carries those replacements in the same atomic storage batch as the head. Only chainstate commit and restore paths write the `coins` family.
- **Disconnect**: `load_block_undo` reads one block's `UndoBatch` as the `UndoRecord` bytes named by the durable head receipt. Disconnect commits reversed coin replacements and head advance in one atomic batch. The raw inverse stays crate-private. Every external disconnect goes through `disconnect_block_admitted`.
- **Read**: `UtxoSet::get` returns the `TxOut` payload, while `get_entry` returns the one `UtxoCoin` shape. Whole-set reads run under `with_stable_view` (`UtxoSetView`). This view also serves the `hash_serialized_3` commitment, script scans, and memory accounting. Windowed apply reads through `WindowWorkspace` over the engine coin store.
- Resident UTXO lookup tables MUST share one process-seeded bucket hasher. Bucket hashes MUST NOT enter persisted keys or coin commitments.
- **Distribution**: production consumers MUST receive `UtxoReader`, never `UtxoSet`, `CoinStore`, or underlying `KvStore` engine capabilities. The reader answers point reads, confirmation-height queries, script scans, and stable whole-set reads. It carries no route to `utxo::contract` or a writable coin store. `Chainstate::utxo`, `Chainstate::utxo_handle`, `Chainstate::coins`, `Chainstate::commit_authority`, `UtxoReader::fixture_set`, and `UtxoReader::fixture_coin_store` are fixture-only seams. Production builds MUST exclude these seams. The g17 production-consumer gate checks this boundary. Shard, record, commit-event, and undo-codec machinery is crate-private with its storage owner.
- Rollback sequencing splits at the marker fence, which is exactly where the crate boundary runs. Chainstate refuses a stale tip before arming. It then executes durable head advance and publication. It disarms the marker only when the commit succeeds.
- The contract surface is `bitcoin_rs_storage::utxo::contract`. The crate root keeps only read, snapshot, and statistics names. RPC and P2P admission read through `UtxoReader` (`UtxoCoin`, `UtxoScan`). Index is the read consumer that decodes the contract's `UndoBatch`. No caller assembles mutations outside tests.
- `CoinStore` is the committed coin authority. Point reads resolve through it. Each `UtxoReader` whole-set query MUST capture one engine snapshot and decode a separate view-owned image. The image MUST remain stable while that view exists. Dropping the view MUST release the derived image even when reader handles survive. Offline `UtxoSet` views borrow their existing set. Read-only snapshot serialization consumes the captured view, not a writable backing handle.
- `UtxoReader::get`, `get_entry`, `has_live_outputs_for_txid`, and `confirmation_height` MUST return `UtxoError` for an engine read or coin-decoding failure. They report absence only when the requested coin or eligible output is absent. A caller MUST NOT treat an error as an absent coin.

Proof: `utxo_queries_expose_no_production_mutation_capability` checks the production interface with isolated consumers. `dropping_last_query_view_releases_derived_image_while_readers_survive` checks query results and released derived allocations. `query_views_keep_independent_committed_snapshots` checks snapshot isolation across a committed change.

### `ARCH-07b`: AssumeUTXO chainstate roles and single active authority

- **Chainstate roles**: `bitcoin_rs_execution::ChainstateRole` defines the lifecycle state of every chainstate. (1) `Ordinary` is the standard fully validated chainstate. (2) `AssumedActive` is the snapshot-loaded chainstate actively driving the node tip. It retains its snapshot base height and block hash. (3) `Historical` is the background chainstate validating from genesis or an accepted historical checkpoint up to the snapshot base height.
- **Single active authority invariant**: at all times exactly one chainstate is the authoritative active chainstate (`Ordinary` or `AssumedActive`). Only the active chainstate drives mempool admission, mining template assembly, RPC/ZMQ chain effects, indexer updates, and pruning execution. The historical chainstate validates with the consensus connect path (`Chainstate::connect`). Its events are detached and never routed to mempool, mining, RPC, ZMQ, or indexers.
- **Snapshot activation and pinned metadata**: activation is coordinated exclusively by `AssumeUtxoManager`. Trust is carried by `bitcoin_rs_storage::utxo::core_snapshot::VerifiedSnapshotState`. This is one owned `UtxoSet` sealed with the base hash, height, `hash_serialized_3`, and `CoinStats` derived from exactly those coins. Its fields are private. No accessor lends the set (the set cannot be mutated in place). Only `into_parts` releases the set, consuming the proof. Neither constructor accepts a digest. `core_snapshot::read_verified` seals portable Core input after the staged record stream commitment matches the compiled anchor. It folds statistics from those authenticated records into the hash table (`CoinStatsAccumulator::with_parallel_muhash`). Sealed stats equal an independent scan under `to_bytes`, not necessarily `PartialEq` on `MuHash3072`. No statistics are computed for a mismatching file. `VerifiedSnapshotState::verify` recomputes the commitment from an owned set. It scans statistics only after the commitment matches. `AssumeUtxoManager::activate_verified_snapshot` (portable `loadtxoutset`) accepts only the state and runs no second commitment pass or statistics scan. It then compares the state's height, base hash, and commitment with the compiled `assume_utxo_for_height` anchor in one install step. Caller-supplied digests and snapshot trailers do not establish trust (this is Core's `HASH_SERIALIZED` commitment, not MuHash). The pinned transaction count seeds the active tip. Historical finalization checks this count independently. The base header must already exist at the pinned height and be valid. It must be an ancestor of the current best-work header tip. The installer rechecks these requirements under transition exclusion before the lifecycle commit. The snapshot base must carry strictly more cumulative work than the settled active tip. Height alone does not order competing branches. Installed coin statistics are the sealed state's, derived once from the imported coins. The installer scans the installed engine coins and refuses a `hash_serialized` that differs from the pinned commitment, then publishes the snapshot-base checkpoint (engine image, header tree, scanned coin statistics) before the lifecycle commit; the checkpoint `CURRENT` is written last. The resolved header supplies chainwork. Installation and role changes serialize with chain transitions. Failed validation publishes nothing.
- **Compiled mainnet anchors and provenance**: `Network::Mainnet.assume_utxo_data()` supports heights 840,000, 880,000, 910,000, 935,000, and 965,000, retaining the earlier anchors. The first four match Bitcoin Core v31.1 chain parameters at `9be056a8a72b624dae9623b2f7bded92c2a21c91`. The 965,000 entry comes from Bitcoin Core v32.0rc1 at `d0231bb01d83178224bf7b198ba04f78cc2c89ef`. Block hashes, `hash_serialized_3` commitments, and cumulative transaction counts are owned by `crates/consensus/src/primitives/network.rs`. These additions leave the project's broader Core compatibility baseline unchanged.
