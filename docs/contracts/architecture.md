# Architecture contract

The normative contract for workspace crate layering, one-way dependency direction, storage engine confinement, and composition boundaries.

These boundaries are internal architecture, not a compatibility promise: a demonstrated better internal design may redraw them, and the `ARCH-06` change process governs layer assignments and workspace dependency boundaries.

Owners:
- `Cargo.toml`, `crates/*/Cargo.toml`, `bin/bitcoin-rs/Cargo.toml`; workspace dependency gate in `bin/bitcoin-rs/tests/gates/g17_dependency_direction.rs`
- `KvStore`, `KvSnapshot`, `PrefixScanLimit`, `PrefixScan` in `crates/storage/src/trait_.rs` (bounded prefix scans, `ARCH-02`)

## Layer model

| Layer | Crates | Responsibility |
| --- | --- | --- |
| 4: Compose | `node`, `bitcoin-rs`, `e2e`, `storage-footprint`, `snapshot` | Runtime assembly, lifecycle, and offline tooling |
| 3: Surface | `rpc` | External protocol boundaries |
| 2: Services | `chain`, `chainstate`, `utxo`, `p2p`, `mempool`, `index`, `mining` | Domain state and services |
| 1: Storage | `storage` | Storage contracts and engine drivers |
| 0: Core | `primitives`, `script`, `consensus` | Protocol types and validation, without storage or I/O |

Crate names use the `bitcoin-rs-` prefix except for the `bitcoin-rs` binary.

## Clauses

### `ARCH-01`: Five-layer one-way dependency direction

- Every workspace crate is assigned to an approved layer (0 to 4); a crate may depend only on crates in the same or a strictly lower layer. Upward or otherwise forbidden edges fail the `g17_dependency_direction` gate. The resolved workspace graph is a directed acyclic graph: any cycle, even within one layer, fails the gate.
- The [layer model](#layer-model) assigns every crate. Layer 0 crates have zero dependencies on storage, network, or filesystem I/O.
- In Layer 2, `chainstate` is the authoritative applied-chain owner: it composes only lower/same-layer protocol, chain, UTXO, and storage capabilities, and MUST NOT depend on mempool, P2P, index, mining, RPC, node, or the binary. `utxo` sits in Layer 2 because it depends on `storage` for undo records and persisted coin statistics. `chain` depends on `consensus` for BIP9 parameters and the BIP113 locktime cutoff, reads no block bodies, and defines the `BlockBodySource` capability consumed by P2P, index, and RPC. `mining` sits in Layer 2 because it depends on `mempool` for candidate selection and on `chain` for candidate header/work/time context.
- `p2p` depends on `mempool` for the transaction inventory view and the committed-mutation relay consumer; `mempool` MUST NOT depend on `p2p`, `rpc`, `node`, or the binary. Admission retains peer attribution as data, never connection ownership; the gate checks this boundary. `p2p` consumes chainstate-owned historical progress, window-failure dispositions, and reorg outcomes without enabling backend features (node retains transition settlement and follower dispatch; P2P consumes outcomes for scheduling, retry, and peer policy through `SyncChain`), and consumes optional compact-filter queries from `index` through `CompactFilterQuery` (index owns generation, persistence, and readiness; no second index runtime in P2P, no storage backend features).
- In Layer 4, the footprint package is an offline Linux filesystem utility with no node/runtime-workspace or storage-engine dependencies; `bitcoin-rs-snapshot` is an offline Core-file inspector and verifier on the shared primitives/UTXO codec composing no node, P2P, RPC, mempool, or mining runtime; `bitcoin-rs-e2e` drives the composed daemon and the pinned reference node over public surfaces only, declares no internal dependencies, and no workspace crate may depend on it.
- Explicit non-goal: layer numbers do not justify speculative new crates or thin wrapper layers. A boundary exists only to isolate external dependencies, enforce safety/consensus boundaries, or separate independent runtime lifecycles.

### `ARCH-02`: Exclusive storage engine dependency ownership

- `bitcoin-rs-storage` is the sole crate permitted to depend on storage engine crates (`fjall`, `redb`, `rust-rocksdb`). No other crate may name an engine dependency in `[dependencies]`, `[build-dependencies]`, or `[dev-dependencies]`. Higher layers reach persistent state only through the `KvStore` facade and storage abstractions. Storage owns journal/checkpoint formats, filesystem operations, durability primitives, and the optional bounded `HistoryAccess` consumer role.
- Bounded prefix scans: `scan_prefix_bounded` and `scan_prefix_from_bounded` on `KvStore` and `KvSnapshot` return a bounded part of one column family's rows under a prefix. `PrefixScanLimit { max_rows, max_bytes }` bounds one scan: `max_rows` caps returned rows (zero returns none); `max_bytes` caps the running total of returned key-plus-value bytes. The first row is exempt (returned even when it alone exceeds `max_bytes`, and counted); each later row is returned only when the total including it stays at or below `max_bytes` (with `max_bytes` 10 and rows of 6 and 5 bytes, the first is returned and the second refused). A row whose byte count overflows `usize` is refused. `PrefixScan { rows, complete }` holds rows in key order; `complete` is true only when the scan reached the end of the prefix with no row refused. An implementation MUST NOT report `complete = true` after refusing a row. An exact-fit limit is complete; a zero-row limit is complete only when no row matches. A store that cannot serve a scan MUST return an error, never an empty or falsely complete scan.
- Seek point: `scan_prefix_from_bounded(cf, prefix, start)` takes an inclusive full-key `start`. Rows begin at the first key at or above the greater of `start` and `prefix` in byte order and end where keys stop beginning with `prefix`. A `start` before the prefix (including the empty slice) begins at the first row; a `start` past every key of the prefix (including one that sorts after the prefix without beginning with it) yields an empty, complete scan. Resuming after returned row `k` passes `k` followed by one zero byte, the least key above `k`.
- Required versus defaulted methods: `iter_prefix` and `scan_prefix_from_bounded` are required on both traits with no default body, so every `KvStore` and `KvSnapshot` MUST provide both. `scan_prefix_bounded` has a default body on both traits that collects from `iter_prefix` under the same limit; implementations MAY override it. The four redb types (`RedbStore`, `RedbSnapshot`, `RedbTxIndexStore`, `RedbTxIndexSnapshot`) override it and apply the limit inside the scan while their `iter_prefix` materializes every matching row; fjall and RocksDB stores and snapshots use the default.
- Backends (fjall `range`, RocksDB `IteratorMode::From`, redb `Table::range`) seek natively to the greater of `start` and `prefix` and never collect-then-discard a prefix head. A scan stops at the first row the limit refuses, so it reads at most one row past the limit and drops it.
- Fixed-width txindex store: `RedbTxIndexStore` and `RedbTxIndexSnapshot` serve `TxConfirmed`, `Funding`, `Spending`, `BlockHeaders`, `ScriptLive`, and `UtxoMeta`; any other column family, or a prefix wider than a fixed-width family's key, returns `StorageError::InvalidOperation`, never an empty scan.
- Snapshot reads see the view captured by `KvStore::snapshot`; rows committed after the snapshot are invisible, and pages read through one snapshot read one view. The limit bounds returned rows only: at most `max_rows` rows and at most the greater of `max_bytes` and the first row's key-plus-value size (an oversized first row is returned whole). It does not bound engine-internal reads or caches, or a transient copy of the row it refuses (the fixed-width txindex value scan copies a row's value before the limit can refuse it).
- Consumers: `bitcoin-rs-index` calls `KvSnapshot::scan_prefix_bounded` for txid, scripthash, spending-outpoint, and live-output lookups (`StoreTxIndexSnapshot::scan`, `live_rows`, `crates/index/src/index/snapshot.rs`); `QueryBudget::next_scan_limit` (`crates/index/src/runtime/query.rs`) derives each limit from the query's remaining row and byte budget; `accept_scan` / `accept_live_scan` turn `complete = false` into `TxUnavailableCause::PrefixScanTruncated` / `LivePrefixScanTruncated`, never a partial answer. Capability reset (`crates/index/src/index/state.rs`) calls `KvStore::scan_prefix_bounded` under `RESET_SCAN_LIMIT` one page at a time. No production code calls `scan_prefix_from_bounded`; storage tests do.
- Proof: `crates/storage/tests/bounded_prefix_scan.rs` (`fjall_bounded_prefix_scan`, `rocksdb_bounded_prefix_scan`, `redb_bounded_prefix_scan`: limit/prefix/seek/paging/snapshot-isolation/oversized-first-row semantics, feature-gated) and `crates/storage/tests/redb_txindex.rs` (`txindex_fixed_prefix_boundaries_12`, `txindex_fixed_prefix_boundaries_80`, `txindex_bounded_scan_empty_values`, `txindex_continuation_seeks_every_fixed_width_family`, `txindex_continuation_snapshot_is_point_in_time`, `txindex_unsupported_column_families_rejected`: rows, `complete`, errors). The at-most-one-row-past-the-limit claim rests on `collect_bounded_prefix` and the redb scan loops (return at the first refused row); the `usize`-overflow refusal rests on `push_bounded_row` (`checked_add`) and has no test.

### `ARCH-03`: Storage backend feature forwarding confinement

- Backend feature forwarding (`fjall`, `redb`, `rocksdb`) is confined to: (1) operator-facing entry points (`bitcoin-rs-node`, `bitcoin-rs`) exposing backend selection to operators and packaging scripts; (2) services-tier adapter crates (`bitcoin-rs-chainstate`, `bitcoin-rs-utxo`, `bitcoin-rs-index`) whose features exist solely so `-p` package builds propagate selection into `bitcoin-rs-storage`; (3) `bitcoin-rs-storage` itself, which owns the concrete backend dependencies and exposes them through the `KvStore` facade.
- Layer 0 (Core) and Layer 3 (Surface / RPC) crates MUST never define or forward storage backend features. `bitcoin-rs-chain`, `bitcoin-rs-p2p`, `bitcoin-rs-mempool`, and `bitcoin-rs-mining` own no storage and MUST NOT define or forward backend feature names; an empty `rocksdb = []` marker counts as defining one and is forbidden. `bitcoin-rs-node` and `bitcoin-rs` may forward selection only into engine-selecting crates (`storage`, `chainstate`, `utxo`, `index`).
- `fjall` is the default shipped backend; `redb` and `rocksdb` are retained shipped alternatives and independent product-matrix comparisons. MDBX had only a diagnostic role with no current consumer and is removed as a complete ownership unit; existing MDBX datadirs are neither migrated nor opened.
- `crates/node/src/storage_backend.rs` is the sole owner of concrete runtime backend construction in the node. Chainstate and txindex each cross that boundary once, then compose backend-neutral capabilities for undo, pruning, journal, indexing, and footprint inspection. The consumer visitor is only a composition seam; `KvStore` owns reads, writes, batches, and durability. The txindex redb lane keeps its specialized fixed-width store and is never widened to the generic redb adapter.

### `ARCH-04`: RPC surface independence from storage

- `bitcoin-rs-rpc` MUST have zero non-test dependency edges on `bitcoin-rs-storage` and zero dependencies on storage engine crates. It consumes node capabilities (chain, mempool, index, network, mining, utxo) exclusively through the capability groups `Context` stores (`ChainHandles`, `MempoolHandles`, `IndexHandles`, `NetworkHandles`, `MiningHandles`), never through direct database access. `Context::from_handles(ContextHandles)` is the single composition point: one `ContextHandles` value carries every capability including the transition-exclusion read role, and production wiring attaches nothing to a built `Context`. `bitcoin-rs-rpc` defines and forwards zero backend features (the bench-only dev-dependency for offline `txoutproof` fixtures is test scope only, documented in `crates/rpc/Cargo.toml`).

### `ARCH-05`: Node composition and orchestration boundary

- `bitcoin-rs-node` (Layer 4) is the assembly and lifecycle orchestration layer: it wires storage backends, consensus validators, mempool gateway, P2P listeners, index reconciliation workers, and RPC services into an executable node runtime. Domain mechanics live in domain crates: consensus rules in consensus/script; mempool admission preparation, retry, orphan bodies and indexes, ready-orphan work, and recent rejects through `MempoolGateway` (plus the fee-estimator history file format and atomic datadir persistence in `fee_history` / `fee-estimator-history.dat`, which node only loads at open and saves at shutdown); connection lifecycle in p2p (transaction inventory implementation, missing-parent requests, source-connection checks, bounded relay queue/worker/saturation policy); template assembly and the mining control contract in mining; index schemas in their owning crates. Node supplies the chain view, connects committed admission results to relay and mining, owns channel wiring and worker startup/shutdown, and keeps no second admission-state store or transaction policy implementation. Admission sequencing follows [MPL-04](mempool-mutations.md); wire behavior and deviations follow [P2P-01](p2p-wire.md).
- `bitcoin-rs-mining` owns `Candidate`, `BlockTemplate`, `MiningInfo`, `MiningControl`, and the candidate lifecycle: the `(applied_tip_hash, mempool_sequence)` generation key, bounded template cache with single-flight assembly, long-poll publication, and BIP22/BIP23 projection (`MiningService`, fed by node-owned capability sources). Mining also owns `MiningGenerationSignal` (authoritative-mutation wake seam, `generation_signal`), `getnetworkhashps` estimation (`network_hashps`), and the BIP22/`submitheader` reject vocabulary (`bip22`). RPC maps those types onto BIP22/BIP23 JSON and caches no templates and runs no long-poll.
- `bitcoin-rs-node` owns runtime startup/shutdown sequencing, configuration resolution and validation (`UserConfig` layers → `NodeConfig`), the mining control facade (`MiningCoordinator`, composing the mining lifecycle service with chainstate read and transition capabilities, submitting solved blocks, requesting header admission from chainstate), watch-only coinbase payout configuration (`MiningConfig::payout_script`, decoded once after every layer against the resolved network), and process-level cache budgeting (`dbcache` across chainstate and txindex namespaces). The node option table (`crates/node/src/options.rs`) declares every operator option once with its value grammar and its spelling on each process-input surface; the `bitcoin-rs` binary expands that table into argv, environment, TOML, and `bitcoin.conf` readers and holds no option name or grammar of its own beyond the two configuration-file selectors and the storage-measurement flags.
- Applied-tip mutation, recovery, checkpoint publication, mandatory retention consumption, and branch switching are owned by `bitcoin-rs-chainstate` (`ARCH-07`), not by a public field bag of subsystem handles. Retained-history *authority* (registry, executed frontier, prune reserve/commit) is owned by `bitcoin-rs-storage::pruning`; node composes that one authority into chainstate, the prune service, and bounded index history.
- `bitcoin-rs-rpc::zmq` owns topics, framing, HWM validation, socket transport, mempool sequence projection, and live notifier enumeration. `bitcoin-rs-node` constructs and wires the publisher and owns when committed chain effects are emitted; the same live publisher sources `getzmqnotifications`, and node keeps no parallel notifier model. The `g17_dependency_direction` gate pins the external `zmq` dependency to the surface crate and permits node only to forward `bitcoin-rs-rpc/zmq`. `ARCH-07` owns transition reservation and post-commit follower dispatch.
- `resolve` folds every layer through `UserConfig::overlay` in precedence order, lowest first: a set field replaces the earlier value, an unset field leaves it, nested override structs merge the same way (including `ChainstateJournalOverrides` and `MiningOverrides`); `overlay` also applies the RPC credential style rule inside the layer being folded, so a later password clears an inherited cookie path and a later cookie path clears inherited user and password. After the fold, the winning `network` value fills the profile-owned fields once via `NetworkProfile::for_selection`, and `rpc_auth` chooses the final credential style from the winning values.
- Proof: `crates/node/tests/unit/config/tests.rs` (`resolve_prefers_higher_layers_field_by_field`, `rpc_cookie_and_credential_layers_keep_one_auth_source`, `earlier_set_fields_survive_a_later_bare_network_selection`); `crates/node/tests/config_layered.rs` (`mining_payout_address_decodes_after_all_layers`); `bin/bitcoin-rs/src/bitcoin_conf.rs` (`every_table_core_key_reaches_its_slot`).

### `ARCH-06`: Hierarchy change and exception process

- Any change to workspace crate layer assignments, introduction of new workspace crates, or addition of cross-crate dependencies REQUIRES: (1) updating the `approved_layer` table or engine crate assertions in `bin/bitcoin-rs/tests/gates/g17_dependency_direction.rs`; (2) updating this contract (`docs/contracts/architecture.md`) with the rationale and invariant justification; (3) passing the `g17_dependency_direction` gate test. Speculative or circular dependency edges violating the one-way flow are rejected by automated gate enforcement in CI.

### `ARCH-07`: Chainstate owns authoritative applied-chain mutation

- `bitcoin_rs_chainstate::Chainstate` is the in-process owner of applied-tip mutation, recovery, branch switching, checkpoint payload assembly/publication, and mandatory retention consumption. `NodeState`, `BlockSync`, mining, and RPC chain-control hold or clone that service; they do not assemble a transition from independent locks. Retained-history *authority* is not chainstate's: `bitcoin-rs-storage::pruning` owns the `RetentionRegistry`, the executed frontier, and prune reserve/commit, and node composition seeds that one registry and distributes it. Chainstate receives [`bitcoin_rs_storage::MandatoryRetention`] for transition pins and the existing bounded `HistoryAccess` role for optional block-input queries; both originate from that same registry, neither can prune, commit, or shut down retention, and chainstate is not a broker for the registry.
- `BlockUndoSource` is implemented directly by `Chainstate`; RPC holds only that read trait. A query captures the caller's applied hash, full durable receipt, and storage-owned history lease under the transition domain; bounded body/undo reads and projection run outside tree/write/transition locks, followed by exact receipt, applied-hash, and lease revalidation. Historical snapshot prefixes need durably archived validation progress: retained bytes alone never establish validation. The current undo extent may certify a disconnected branch until a later receipt replaces it.
- `Chainstate::begin_transition` and `TransitionLock::into_transition` are the only constructors of a `ChainTransition`. Reorg planning that must abort without mutating takes `lock_transition` first and promotes it with `into_transition` only after the authoritative plan matches the preloaded plan.
- Snapshot reads (`Chainstate::snapshot`) copy the independently published header tip and a coherent applied-tip / chain-tx-count pair; they take no transition lock and cannot mutate chainstate. `ChainEventPublisher` cells remain a separate coherent applied-tip snapshot for index consumers (`EVT-01`).
- Long-lived RPC, P2P, index, and mining consumers receive `TipReader`, `BlockTreeReader`, and `StableRead` capabilities. Readers expose snapshot load and tree read guards; every `&self` tree accessor is a pure read, and the tip publication cell is shareable only through `&mut BlockTree`. `StableRead` excludes authoritative transitions while a coherent read runs; its only production verbs are `lock` and bounded `try_lock_for` (zero timeout = immediate attempt), it hands back an opaque guard, and it exposes no route to its matching `TransitionAuthority` (the role chainstate and destructive pruning hold across a mutation). `NodeState::open` mints one `TransitionDomain` per node and distributes matching roles to production consumers. `Chainstate` publishes no fence: `Chainstate::read_fence` does not exist and the g17 facade gate denies it. This is a production-wiring guarantee, not type-level provenance: `TransitionDomain::new`, `Default`, and `stable_read` are public, and `ChainHandles::default` in the public `Context::new` fixture mints a private domain, so passing such a role to a live node reader does not exclude that node's transitions. Header admission uses `Chainstate::admit_headers`; normal genesis connect publishes through the tree's shared tip cell with no separate fallback. Short-lived `ChainAdmissionView` values borrow readers; the P2P transaction ingress worker acquires its owned readers once at startup.
- `Chainstate::validate_block` dry-runs the apply path's pre-write consensus gates under `lock_transition`, takes no mempool generation, and persists nothing. BIP22 proposal omits proof-of-work; every other pre-write gate is the same function commit runs. Owner: `crates/chainstate/src/lib.rs`. Authoritative apply lives in `crates/chainstate`, which holds and imports no mempool, RPC, ZMQ, index, mining, P2P, or node types. Apply publishes the tip and returns a `ConnectOutcome` or `DisconnectOutcome`; capture flags are set at construction so apply can produce `rawtx` and canonical block bytes without holding the consumers.
- Node owns cross-domain sequencing around a chain transition: it reserves the mempool generation, dispatches `ChainFollowers`, then publishes the stable mempool generation before the chain transition is dropped. Follower-free convenience methods are compiled for tests or the `test-seam` capability only; in-workspace production dependencies and feature forwarding MUST NOT enable that capability: production uses explicit transitions plus follower settlement, and downstream users may explicitly opt into `test-seam`. RPC `BlockLog`, hash/raw ZMQ, TxIndex wake, sequence `C`/`D`, mining generation, admission, block-confirmation eviction, and reorg reconsideration run from node-owned dispatch; consumer failure cannot invalidate chainstate. Issue #77 owns the durable event journal; this is dependency direction, not a second event contract. Cross-store ordering MUST NOT be pushed into `utxo` or `storage`.
- Reorg planning, body retention/loading, disconnect/connect execution, invalidation, and checkpoint-debt settlement live in chainstate. Node supplies a `ReorgObserver` for mempool/follower effects and holds the mempool generation fence around the operation. Reorg body memory is bounded by the chainstate streaming window; no whole departed branch is retained.
- Runtime capability ownership stays with the mutating subsystem: `P2pService` owns peer sessions, bans, the network-active latch, and header/block/outbound channels; `ChainFollowers` owns the RPC block log, ZMQ publisher, and mining-generation signal; `Chainstate` owns the IBD latch. `NodeState` composes those services and returns their handles without retaining parallel fields. Its inbound transaction channel is node-owned because node orchestration drains it into `MempoolGateway`. Confirmed transaction bodies are queried through the derived index and durable block storage, never through a second node/RPC transaction map. RPC network answers and control operations read and mutate network state through `P2pService` directly (peer table, traffic counters, ban list, added-node list, network-active latch; bans, added nodes, network-active toggling, disconnections via service control methods); RPC receives no raw handles for bans, added nodes, the latch, or the outbound dial channel, and there is no parallel RPC-local network-state projection or duplicate mutation authority.
- `MempoolGateway` owns the process mempool handle; `NodeState::mempool` is a borrowed read/composition capability, not a parallel retained `Arc`. Gateway interning is the public one-gateway-per-pool-ledger enforcement boundary for test seams and downstream composition: the ledger is `bitcoin_rs_mempool::Mempool` (defined in `crates/mempool/src/pool.rs`, re-exported at the crate root since `mod pool` is private), the entry arena plus derived txid/wtxid/funding/spending/priority indexes behind the gateway's `Arc<RwLock<Mempool>>` handle; production constructs that same owner once. `NodeState` retains `PruneService` as a node/storage mutation capability because it is created only after chainstate supplies prune authority and is handed to the later RPC lifecycle; it contains no duplicate block or transaction projection.

### `ARCH-07a`: Chainstate mutates `utxo` through one narrow contract

`bitcoin-rs-utxo` is not a second mutation authority: it holds the live coin set and the persistence formats, and chainstate drives it through one coherent apply/commit/disconnect contract (`crates/utxo/src/contract.rs`).

- **Apply**: `build_block_changes` turns one validated block into its `BlockChanges`, its `UndoBatch`, and the `BlockValueTotals` the coinbase check needs. Resolved prevouts enter through `SpentOutputLookup`; the live set at BIP30 exception heights enters as the optional overwritten lookup. **Commit**: `contract::commit_block_changes` applies one block's `BlockChanges` and emits commit events to the single attached `CoinStatsListener`; the set's raw mutator is crate-private.
- **Disconnect**: `persist_block_undo` / `load_block_undo` round-trip one block's `UndoBatch` as the `UndoRecord` bytes the durable head receipt names, and `rollback_block` applies that batch under the durable disconnect marker plus the coinstats rewind. The raw inverse (`UtxoSet::undo_block`) is crate-private: every external disconnect goes through `rollback_block`.
- **Read**: `UtxoSet::get` returns the `TxOut` payload while `get_entry` returns the one `UtxoCoin` shape; whole-set reads run under `with_stable_view` (`UtxoSetView`), which also serves the `hash_serialized_3` commitment, script scans, and memory accounting. Windowed apply reads through `WindowOverlay` over the same `OutputSource`.
- **Distribution**: production consumers receive `UtxoReader`, never the set. It answers `get`, `get_entry`, `has_live_outputs_for_txid`, `scan_script_pubkeys`, and the two stable whole-set reads, and carries no route to `utxo::contract`. `Chainstate::utxo` and `Chainstate::utxo_handle` are fixture-only seams, and `UtxoReader::fixture_set`, the one route back to the set, is compiled out of production builds, so the g17 facade gate can deny all three from an isolated production consumer. Shard, record, commit-event, and undo-codec machinery is crate-private.
- Rollback sequencing splits at the marker fence, which is exactly where the crate boundary runs: `utxo::contract::rollback_block` owns the fenced set mutation (arm the marker, undo the set, rewind coinstats, complete the marker) and nothing beyond it. Chainstate owns everything around that fence (refusing a stale tip before arming, then journal rewind, durable head advance, and publication) and disarms the marker only when the journal rewind succeeds; otherwise a matching clean checkpoint disarms it after publishing the rolled-back set (`ARCH-07` owns this surrounding order and durability policy).
- The contract surface is `bitcoin_rs_utxo::contract`; the crate root keeps only read, snapshot, and statistics names. RPC and P2P admission read through `UtxoReader` (`UtxoCoin`, `UtxoScan`); index is the read consumer that decodes the contract's `UndoBatch`. None assembles mutations outside tests, which build fixture sets through `BlockChanges` + `commit_block_changes` on `fixture_set()`.

### `ARCH-07b`: AssumeUTXO chainstate roles and single active authority

- **Chainstate roles**: `bitcoin_rs_chainstate::ChainstateRole` defines the lifecycle state of every chainstate: (1) `Ordinary` (standard fully validated chainstate); (2) `AssumedActive` (snapshot-loaded chainstate actively driving the node tip, retaining its snapshot base height and block hash); (3) `Historical` (background chainstate validating from genesis or an accepted historical checkpoint up to the snapshot base height).
- **Single active authority invariant**: at all times exactly one chainstate is the authoritative active chainstate (`Ordinary` or `AssumedActive`). Only the active chainstate drives mempool admission, mining template assembly, RPC/ZMQ chain effects, indexer updates, and pruning execution. The historical chainstate validates with the consensus connect path (`Chainstate::connect`) but its events are detached and never routed to mempool, mining, RPC, ZMQ, or indexers.
- **Snapshot activation and pinned metadata**: activation is coordinated exclusively by `AssumeUtxoManager`. Trust is carried by `bitcoin_rs_utxo::core_snapshot::VerifiedSnapshotState`: one owned `UtxoSet` sealed with the base hash, height, `hash_serialized_3`, and `CoinStats` derived from exactly those coins. Its fields are private, no accessor lends the set (`UtxoSet::replace_from` mutates through `&self`), and only `into_parts` releases the set, consuming the proof; neither constructor accepts a digest. `core_snapshot::read_verified` seals portable Core input after the staged record stream's commitment matched the compiled anchor, folding statistics from those authenticated records into the hash table (`CoinStatsAccumulator::with_parallel_muhash`: sealed stats equal an independent scan under `to_bytes`, not necessarily `PartialEq` on `MuHash3072`); no statistics are computed for a mismatching file. `VerifiedSnapshotState::verify` recomputes the commitment from an owned set and scans statistics only after it matched. `AssumeUtxoManager::activate_verified_snapshot` (portable `loadtxoutset`) accepts only the state and runs no second commitment pass or statistics scan; `activate_snapshot_state` (native v4 embedding input, arriving without a proof) runs `verify` exactly once under the lifecycle lock, after the untrusted-height, already-active, full-revalidation, and base-hash refusals. Both entries then compare the state's height, base hash, and commitment with the compiled `assume_utxo_for_height` anchor in one install step. Caller-supplied digests and snapshot trailers do not establish trust (this is Core's `HASH_SERIALIZED` commitment, not MuHash). The pinned transaction count seeds the active tip and is independently checked during historical finalization. The base header must already exist at the pinned height, be valid, and be an ancestor of the current best-work header tip; the installer rechecks these under transition exclusion before the lifecycle commit. The snapshot base must carry strictly more cumulative work than the settled active tip: height alone does not order competing branches. Installed coin statistics are the sealed state's, derived once from the imported coins; archiving the set as native v4 for activation (`write_coins_sealed`) walks the table to serialize it but emits the sealed `stats.muhash.finalize()` trailer instead of refolding MuHash. The recomputing `write_coins` remains as the test-only oracle for proof-less crash fixtures. The resolved header supplies chainwork. Installation and role changes serialize with chain transitions; failed validation publishes nothing.
- **Compiled mainnet anchors and provenance**: `Network::Mainnet.assume_utxo_data()` supports heights 840,000, 880,000, 910,000, 935,000, and 965,000, retaining the earlier anchors. The first four match Bitcoin Core v31.1 chain parameters at `9be056a8a72b624dae9623b2f7bded92c2a21c91`; the 965,000 entry comes from Bitcoin Core v32.0rc1 at `d0231bb01d83178224bf7b198ba04f78cc2c89ef`. Block hashes, `hash_serialized_3` commitments, and cumulative transaction counts are owned by `crates/primitives/src/network.rs`. These additions leave the project's broader Core compatibility baseline unchanged.
- **Snapshot format and interoperability evidence**: the embedding file activation API reads native bitcoin-rs v4 snapshots; `loadtxoutset` uses the shared Core portable v2 reader and the existing activation owner; `getchainstates` projects that owner's lifecycle (`API-33`). Process coverage uses a genuine Core-produced regtest-200 artifact. Compiled mainnet anchors alone establish no hosted artifact availability, mainnet interoperability, or memory/throughput qualification. Portable input must keep Core's dump layout (one group per txid in strictly increasing byte order with unique output indices), and the commitment is computed over that staged stream; a file repeating txid groups is refused before activation (`SnapshotError::TransactionOrder`, RPC `-22`). Core 31.1 accepts such a file built from the regtest-200 artifact: `coins_loaded` 400 while `gettxoutsetinfo` shows 200 txouts with `hash_serialized_3` `17dcc016d188d16068907cdeb38b75691a118d43053b8cd6a25969419381d13a`, identical to the valid case. This is a recorded compatibility divergence, not a stricter-safety claim; matching Core would take the commitment and statistics fold over the de-duplicated coins view instead of the stream, while the trust rule is unchanged. No Core insert-path mechanism is claimed here, only these recorded values. The verified-state cutover is a single-verification ownership contract, not a performance qualification: no performance gain is claimed.
- **Background validation and convergence**: the historical chainstate validates blocks up to the snapshot base height and refuses to connect past it or off the expected target hash (`ApplyError::ConnectPastHistoricalTarget`, `ApplyError::HistoricalTargetHashMismatch`). At the base height the reconstructed `hash_serialized_3` and cumulative transaction count must match the pinned metadata: if valid, the active chainstate transitions `AssumedActive` → `Ordinary`, the historical chainstate retires, and disk status is marked `Finalized`; if invalid, the manager persists `AssumeUtxoDiskStatus::Failed`, marks the active chainstate permanently closed for recovery (`Chainstate::fail_closed_for_recovery`), and refuses subsequent restarts to protect operator data. Historical replay uses its own isolated coins, transient durable-head and undo stores, no body writer, and detached events; the manager archives validated body locators and undo records with lifecycle progress in the active durable-head batch, advancing `commit_id` while preserving tip and transaction count and publishing no active-chain notification. Transient undo is released after the archive receipt. Historical progress checkpoints reuse the chainstate checkpoint format in a separate namespace; the durable head records the accepted generation, height, and hash, and startup restores that checkpoint and replays only its certified archive suffix (genesis replay without an accepted checkpoint). The summary exposes live progress separately. Historical publication retains earlier generations until the head accepts the replacement; recovery selects the head's generation independently of `CURRENT`. Snapshot activation refuses an unresolved full-revalidation marker. Replaying a block covered by an archive receipt does not rewrite its body or progress. Before checking a new body the manager syncs staged bytes and commits a pending-validation reference in the same root; a crash or terminal-status write failure leaving that reference makes startup reconstruct dependencies and complete the check before returning node state, and a mismatch cannot be forgotten by restarting after a failed `Failed` write. Finalization is durable before the role becomes `Ordinary`; unresolved storage errors close both admissions. Production sync pipelines bodies on the pinned base ancestry through a separate instance of the existing download window and block stager: at most 32 pending and staged bodies total, 16 in flight per peer, 64 MiB of staged wire payload plus the stager's one-front-body allowance against full-tail deadlock (decoded bodies occupy bounded memory alongside wire payloads; smaller configured budgets still apply). Archive-capable peers supply batches under the shared download policy (connection leases, timeouts, retry, backpressure) with body binding checked before staging. Each historical pass makes at most nine chain-owner calls, replaying at most eight retained blocks each, admitting at most eight staged bodies in pinned ancestry order and refilling the window while later bodies stay staged; a sync tick runs a pass before and after draining deliveries. Replay retires overtaken downloads; completion clears transient staging. Only validation publishes body locators and lifecycle progress; foreground and historical deliveries have separate owners. Mainnet throughput and absolute restart-latency guarantees remain unproven follow-ups to #1288; the restart contract is bounded by the historical checkpoint interval once an accepted checkpoint exists.
- **Reorg and pruning constraints**: reorgs on `AssumedActive` cannot disconnect blocks at or below the snapshot base height (`ApplyError::DisconnectBelowSnapshotBase`). `PruneAuthority::begin` refuses prefix pruning while either chainstate holds a snapshot role: even a requested height above the base would delete required history. The role check shares the chain-transition lock with activation and finalization, so pruning cannot race a role change.
- **Operator observability**: `AssumeUtxoManager::chainstates_summary` projects both chainstates (roles, tips, validation progress, commitments) without exposing lock primitives.
- **Durable activation and recovery**: immutable coin and header archives sync before the active head commits the pinned base and lifecycle status; that head is the only activation authority and orphan import files never activate a snapshot. Each exclusively created temporary reservation is file-locked before writing and stays locked through rename and directory sync. Before publishing a recovered manager, cleanup probes that lock and reclaims only exact generated reservation names in compiled base directories. Coin reservations must contain native-v4 metadata matching the pinned base; header reservations are recognized only by the network's genesis-header prefix, not by validating a complete header archive. Files open without following symlinks (`O_NONBLOCK` on Unix); the opened descriptor must identify a regular file before locking or reading. Live writers, special files, unknown names/formats, unidentifiable fragments, symlinks, and final archives are preserved. Cleanup failure retains extra files for retry; it can never reset the accepted head or truncate an operator artifact. Startup admits the current schema, validates the root's network pin, and restores a compatible checkpoint or verifies the snapshot archive, then replays the certified foreground suffix to the head. A checkpoint remains an accelerator, including after finalized history is pruned. Activation detaches the old checkpoint journal; anchored recovery does not replay that journal across the snapshot jump. Node-owned mempool reconciliation follows [MPL-04](mempool-mutations.md#mpl-04-generation-validated-admission-and-chain-change-fencing). Activation wakes index/mining consumers without per-block ZMQ events for imported history. Historical undo makes below-base reorgs possible after finalization; crossing below the base removes the snapshot anchor in the disconnect's authoritative batch.

### `ARCH-08`: Durable pruning and reorg retention

- Transaction-cache pruning MUST NOT remove transactions from a block above the durable checkpoint's reorg-retention floor. A requested prune height becomes eligible only after durability is published through `CORE_REORG_SAFETY_MARGIN`, protecting reconsideration of disconnected transactions during reorg handling.

### `ARCH-09`: Authoritative owners and read-only capability boundaries

- Active-tip waits use `chain::ActiveTipWait`, implemented directly by `Chainstate` and composed in RPC's `ChainHandles`. The existing applied-tip ArcSwap remains the sole published tip; one owner-local mutex/condition variable coordinates publication and cancellation. Waiters release that gate before acquiring transition exclusion. Each RPC dispatcher owns its request budget and service cancellation latch, not another chain tip or event history.
- Exactly one authoritative mutation owner exists per piece of state; external consumers and cross-subsystem adapters receive read-only capabilities or single-consumer ownership, never cloneable mutable handles. `BlockLog` is owned and mutated exclusively by `ChainFollowers`; RPC handlers, the derived index runtime, and node queries use the read-only `BlockLogReader` (mutation via `BlockLogReader::write` and raw handles via `BlockLogReader::raw_handle` are gated behind `test-seam`). P2P ingress channels are single-consumer: receivers (`inbound_headers_rx`, `inbound_blocks_rx`, `inbound_tx_rx`) move by value to their worker loops (`BlockSync`, `spawn_tx_ingress_consumer`) through single-take accessors; cloneable `Arc<Mutex<Receiver<...>>>` handles in production wiring are prohibited. `Chainstate` owns the block tree, applied/header tip cells, and the process shutdown signal; construction via `ChainstateParts` consumes `BlockTree` by value and `restored_applied_tip: Option<TipSnapshot>`, eliminating construction-time mutable handle leaks, and mutation authority stays confined to chainstate methods while externals observe tip state via `TipReader` and `BlockTreeReader`. Cancellation and ban state are exposed through read-only `LatchReader` / `BannedReader`; workers query ban status and observe shutdown without mutable handles or raw atomic pointers, and shutdown mutation stays behind `request_shutdown()` and dedicated lifecycle handlers.
- Intentional `Arc` / `Weak` sharing: `Arc<PeerTable>` among P2P service, connection listeners, sync, and RPC network handles (`PeerTable` is internally synchronized and owns peer leases and address tracking); `Weak<MempoolGateway>` held by the P2P transaction relay observer (`LocalTxRelayObserver`) so observer registration neither cycles nor prolongs gateway lifetime; `UtxoReader` as the read-only projection of the authoritative `UtxoSet` (mutated solely by chainstate under transition locks) to mempool and RPC; `InitialBlockDownload` supplying the shared IBD decision across sync and header presync by observing chain progress through `TipReader` / `BlockTreeReader`, with worker orchestration in `BlockSync`.

### P2: typed historical-prefix query with scoped absence (implemented)
