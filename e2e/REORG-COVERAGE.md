# Reorg regression mapping (#1190 / #1280)

This is the reorg/chainstate/mempool slice of [#1190](https://github.com/gosuda/bitcoin-rs/issues/1190). General initial block download, peer stalling/failover, and broad sync convergence stay with that umbrella issue. These process tests exercise the public RPC/P2P/ZMQ surfaces; they do not assert an internal queue or lock shape.

| Bitcoin Core 31.1 reference | Observable property | bitcoin-rs process test | Oracle |
| --- | --- | --- | --- |
| [`feature_block.py`](https://github.com/bitcoin/bitcoin/blob/v31.1/test/functional/feature_block.py) competing and invalid chains | Equal-work header does not displace the applied chain; a strictly higher-work valid branch does. A consensus-invalid higher-work branch cannot change committed coins, and the old chain can still advance. | `e2e/tests/reorg_state.rs`: `invalid_higher_work_body_cannot_change_active_chain`; `crates/chain/tests/header_sync_roundtrip.rs`: `duplicate_equal_work_competing_child_returns_original_id_and_does_not_reorg` (equal-work tie; in-process header-tree evidence, not a process test) | Core-mined block templates and headers; live Core chain/UTXO RPC for the valid switch; a pinned Core process rejects the exact over-subsidized body as `bad-cb-amount`. |

The rejected-branch recovery is compared with its pre-attempt tip, work and MuHash; pinned Core rejects the exact invalid body. The deep-reorg comparison covers live mempool reconciliation. `savemempool`/mempool reload are not implemented, so the post-crash assertion covers durable chainstate rather than mempool persistence. Exact notification ordering is checked against Core's published behavior; the test does not subscribe to a live Core publisher. Concurrent coherent-snapshot behavior during a branch switch remains covered by the owner-level chainstate/RPC generation tests, not by a guaranteed process-level midpoint observation.

CI runs the deterministic process suite in `scripts/ci-pr.sh test-workspace` after provisioning the pinned Core binary. The ZMQ process test has an explicit `zmq` profile in that lane so its feature-gated subscriber cannot silently run zero tests. Raw launch, RPC, and P2P evidence is retained under `target/process-harness/e2e/` by the CI artifact upload.
